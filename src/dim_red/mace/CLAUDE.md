# CLAUDE.md

Guidance for `src/dim_red/mace/` (moved out of the repo-root `CLAUDE.md` since it's specific to this directory).

`mace/` wraps a **frozen, pretrained** MACE model (Batatia et al. 2022 -- equivariant message passing with higher-order tensor products, capturing 3-body/angular interactions natively, unlike `dim_red.cgcnn`'s pairwise-only graph) via [`mace_jax`](https://github.com/ACEsuit/mace-jax), an external JAX/Flax port of MACE. Unlike every other body in this codebase (`vae`/`autoencoder`/`supcon`/`cgcnn`), **this model_kind never trains anything**: `model_kind: mace` runs are a single forward pass through an already-pretrained foundation-model checkpoint (e.g. MACE-MP-0). There is deliberately no `training.py` in this package. A classifier on top of its embeddings comes entirely from `dim_red.pipeline.tail_training` (phase 2, the same architecture-agnostic tail machinery `supcon`/`cgcnn` already reuse) -- see `RunConfig.tails`/`dimred-train-tail`.

## Why `mace_jax` instead of a from-scratch reimplementation

`dim_red.cgcnn` was hand-reimplemented in JAX/Flax specifically because no graph-NN library was available in this codebase's environment and no pretrained-weights story was needed (CGCNN trains from scratch on this project's own dataset). Neither holds for MACE: reimplementing an equivariant architecture faithfully enough to load real pretrained foundation-model weights is a much larger undertaking than CGCNN's from-scratch graph convolution, and an official, actively maintained JAX port already exists. `mace_jax` even supports importing pretrained Torch MACE checkpoints directly (its own `mace-jax-from-torch` CLI), so the "avoid torch as a runtime dependency" principle `cgcnn/CLAUDE.md` established is preserved: torch is needed only for the one-time, out-of-band checkpoint conversion below, never by `dim_red` itself at run time.

## Environment setup (one-time, outside this codebase's runtime)

1. Install `mace_jax` into the `dmred` environment: `pip install git+https://github.com/ACEsuit/mace-jax`. In practice (0.2.0) this pulls in `torch` transitively (as a real, non-optional dependency of `mace_jax` itself, not just of the conversion step) -- the "torch never touches dim_red's own runtime" property still holds (`dim_red.mace` never imports `torch`), it's just no longer true that `mace_jax` alone is torch-free.
2. Install `mace-torch` too (`pip install mace-torch`) -- needed for `mace-jax-from-torch`'s `from mace.tools.scripts_utils import extract_config_mace_model` import; `mace_jax` alone doesn't vendor this.
3. Convert a pretrained Torch foundation-model checkpoint (e.g. MACE-MP-0) into MACE-JAX's own format: `mace-jax-from-torch --foundation mp --model-name small --output <name>.npz`, producing `<name>.npz` (params, see below) + `<name>.json` (architecture config). `MaceConfig.checkpoint_path` points at `<name>` (with or without the `.npz` extension, both accepted).

## Verified against a real `mace_jax` install (0.2.0, 2026-09)

An earlier version of `model.py` was written blind against `mace_jax`'s source read remotely and turned out wrong on several points once `mace_jax` was actually installed and run -- `model.py`/`graph.py` have since been fixed and this has been exercised end to end (`dimred-run` with `model: mace` all the way through an auto-trained classification + visualization tail). The corrections, for anyone touching this again:

- `mace_jax.modules.models.MACE` is a Flax **NNX** module, not Linen -- there is no `.apply({"params": ...}, ...)` convention; a loaded checkpoint's `graphdef`/`params` are called as `graphdef.apply(params)(data, ...)`.
- `mace-jax-from-torch --output foo.npz` does not write a real `.npz` (numpy zip archive) despite the extension -- it's raw `flax.serialization.to_bytes(...)` (msgpack) bytes of an NNX state dict. Loading it requires rebuilding the same graph structure first and restoring state into it as a template; `model.py` reuses `mace_jax.tools.bundle.load_model_bundle` for this rather than reimplementing it.
- The model's forward-pass input dict (`node_attrs`, `node_attrs_index`, `edge_index`, `shifts`, `unit_shifts`, `batch`, `ptr`, `cell`, optionally `head`) is built by `mace_jax.tools.gin_model._graph_to_data` from a (possibly padded) `jraph.GraphsTuple` -- not the simpler ad-hoc dict `dim_red.mace.graph` used to build directly (see that module's docstring: it's no longer wired into `model.py` at all, kept only as a standalone, dependency-free description of a structure's neighbor graph).
- Padding a batch with `jraph.pad_with_graphs` before calling the model isn't just a JIT-shape-stabilization nicety -- `mace_jax`'s own `MACEJAXCalculator`/`mace_jax_predict` CLI both always pad (at least one spare node/edge/graph), so `model.py` does too.
- A few static/config-like NNX state leaves (e.g. `_normalize2mom_consts_var`) are wrapped in `mace_jax`'s own `ConfigDict`, a custom-registered *single-leaf* pytree node -- `flax.serialization.to_bytes` chokes trying to msgpack a raw `ConfigDict`, but replacing it with an equivalent plain `dict` changes the pytree's leaf count, breaking `graphdef.apply` (its intended structure is a match-the-original-graphdef exercise, not a free-form dict). `load_frozen_checkpoint` returns *two* params pytrees to resolve this: `"params"` (`ConfigDict` recursively flattened into plain `dict` -- safe for `flax.serialization.to_bytes`, i.e. what `dim_red.pipeline.single_run.run_single` writes to `model_params.msgpack`, a pure unread-back reproducibility record for this model_kind, same as `supcon`'s `projection_params.msgpack`) and `"params_for_apply"` (the original, `ConfigDict`-preserving pytree -- what `MaceEncoder._encode_chunk` actually calls `graphdef.apply` with).

## `graph.py` (pure NumPy + ASE, no jax dependency, unused by `model.py`)

`atoms_to_mace_graph(atoms, r_max)`/`atoms_list_to_mace_batch(atoms_list, r_max)` build a lightweight, dependency-free (no `jax`/`mace_jax` import) description of one/many structures' neighbor graphs -- real atomic numbers, `edge_index` (`ase.neighborlist.neighbor_list("ijS", ...)`), real-space periodic-image shift vectors. Still correct for what they compute (covered by `tests/test_mace_graph.py`) but **not** what `model.py` actually feeds the model (see above) -- `mace_jax.data.config_from_atoms`/`graph_from_configuration` are used directly there instead, since that's the shape (`jraph.GraphsTuple`) `mace_jax`'s own `gin_model._graph_to_data` adapter expects.

## `model.py`

`MaceEncoder(checkpoint_path, r_max, pooling="mean", max_nodes_per_batch=1024, max_edges_per_batch=4096, max_graphs_per_batch=64)` loads a converted checkpoint via `load_frozen_checkpoint` (wraps `mace_jax.tools.bundle.load_model_bundle`) and validates `r_max` against the checkpoint's own recorded cutoff (raises on mismatch rather than silently using the wrong one). `encode(atoms_list) -> (n, mace_dim)`:

1. Builds one `jraph.GraphsTuple` per structure via `mace_jax.data.config_from_atoms`/`graph_from_configuration` (raises if a structure contains an element outside the checkpoint's own species table).
2. Greedily bin-packs structures into chunks that fit a padded-batch budget (`max_nodes_per_batch`/`max_edges_per_batch`/`max_graphs_per_batch` -- a variable number of structures per chunk, not a fixed count) and pads every chunk to that same shape via `jraph.batch_np` + `jraph.pad_with_graphs`, so the forward pass JIT-compiles once per `encode()` call and is reused for every chunk regardless of what's actually in it. This is deliberately *not* a fixed structure-count-per-chunk batch size: because unit-cell size varies a lot across a typical `dim_red` dataset (pyxtal can generate very small cells, which can have far more neighbor-list edges within a several-angstrom `r_max` than a larger cell of the same structure count, from replicated periodic images -- and `augmentation.supercell_radius` can independently produce much *larger* structures for the same reason from the other direction), padding to `batch_size * worst_single_structure_size` -- the natural first design -- blows up to a many-GB intermediate tensor and OOMs the GPU the moment one outlier structure is much larger than the rest of the dataset; a node/edge/graph *budget*, greedily packed, avoids that. The three `max_*_per_batch` constructor args are a **floor**, not a hard cap: `encode()` computes `max(configured_floor, largest_single_structure_in_this_call + 1)` per axis, so a dataset with one atypically large structure (observed in practice: a 100-structure/family pyxtal run with `supercell_radius: 4.0` augmentation produced a 120-atom/11,520-edge outlier against defaults sized for a `structures_per_family: 40`, no-augmentation smoke test) grows the padding budget to fit it automatically instead of raising.
3. Calls `graphdef.apply(params_for_apply)(data, compute_force=False, compute_stress=False, compute_node_feats=True)` per chunk (`data` from `mace_jax.tools.gin_model._graph_to_data`), reads the `"node_feats"` key (per-atom features, concatenated across every interaction layer), and pools per-structure via a plain `np.add.at`-based segment-sum over the real (non-padding) nodes' graph index (mean or sum, per `pooling`).

`self.params` (the `flax.serialization.to_bytes`-safe copy -- see above) never changes after construction; `self._params_for_apply` is what forward passes actually use. Mirrors `dim_red.cgcnn.model.CGCNNEncoder`'s external shape just enough to slot into the pipeline (`encode`, `self.params` for save/load uniformity), but has no architecture-hyperparameter constructor (the architecture is whatever the checkpoint says) and no `classify_family`/`classify_spacegroup` at all.

**Throughput note**: a MACE-MP-0 (`small`) forward pass is comparatively expensive per structure (~0.3s/structure observed end to end, including per-structure ASE neighbor-list construction, for a 3-family/40-per-family pyxtal smoke dataset on a single modest 8GB GPU) -- a round-15-scale run (7 families x 500 x 5x augmentation = 17,500 structures) is a roughly 1.5-2 hour one-time dataset-build cost before any training even starts, though `pipeline.dataset_cache`'s existing MACE-embedding cache (keyed by a `"mace-pyxtal-"`-prefixed hash) means that cost is paid once, not per sweep point.

## `pipeline` integration (see `src/dim_red/pipeline/CLAUDE.md` for the general `RunConfig`/`model_kind` dispatch pattern this follows)

- `pipeline.config.MaceConfig` (YAML: top-level `mace:` block -- `checkpoint_path`/`r_max`/`pooling`) is used *instead of* `soap:`/`graph:` for `model_kind: mace`. Unlike `GraphConfig`, there is **no** `latent_dim` field reused from `vae:` -- the embedding width is whatever the loaded checkpoint produces, read off the array itself at run time, not a config choice. `RunConfig.__post_init__` requires `mace.checkpoint_path` to be set whenever `model_kind == "mace"` (a frozen body has nothing else to build its weights from).
- `pipeline.dataset_cache.build_mace_dataset_for_run` (+ `get_or_build_mace_dataset`/`get_or_build_pyxtal_mace_dataset`) is structurally the **SOAP-shaped** counterpart, not the CGCNN-graph-shaped one: since the body never trains, there's no reason to cache padded per-atom graph arrays for a training loop the way `build_graph_dataset_for_run` does -- the *final pooled per-structure embedding* is cached directly (`_MACE_CACHE_ARRAY_KEYS` reuses the exact same schema as `_CACHE_ARRAY_KEYS`, feature_mean/feature_std included), keyed by a `"mace-"`/`"mace-pyxtal-"`-prefixed hash so it can never collide with a SOAP or cgcnn cache entry. `_compute_mace_and_standardize` runs a frozen `MaceEncoder` forward pass then standardizes the result the same way SOAP features are (`dim_red.utils.fit_standardization`/`apply_standardization`) -- kept for consistency with `dim_red.pipeline.benchmark`'s kNN/silhouette metrics and so `dim_red.pipeline.inference` can standardize newly-applied structures without recomputing anything on the training set.
- `pipeline.single_run.run_single`: an `is_mace` branch parallel to `is_cgcnn`/`is_supcon`, but with **no training call at all** -- `train_config`/`history` stay `None`/`{}`, and the epoch-logging/`loss_history.csv`-writing steps are skipped entirely (guarded by `if history:`) since there's no loss to report. The "apply the trained encoder to every point of the dataset" step that every other model_kind runs is also skipped for mace -- `mu_all = X` directly, since `build_mace_dataset_for_run` already computed and standardized every point's embedding at dataset-build time; re-running the frozen forward pass a second time would be pure waste. `embeddings_payload` falls into the same (non-cgcnn) branch every SOAP-based kind uses -- `feature_mean`/`feature_std` always present, `features` present when `save_features=True` -- since mace's `X` is SOAP-shaped. The post-hoc family/spacegroup-probability inference block (guarded `if use_family and not is_supcon and not is_mace`) is skipped for mace too: a frozen body has no classifier heads of its own, exactly like `supcon`. The auto-tail guard is `(is_supcon or is_cgcnn or is_mace) and config.tails is not None` -- for `mace`, `tails` is the *only* way to get a classifier out of a run at all.
- `pipeline.inference.load_trained_run`: an early `model_kind == "mace"` branch takes `feature_mean`/`feature_std` directly from `embeddings.npz` (always present for this model_kind -- there's no "pre-existing run predating this field" fallback case, since `mace` didn't exist before that field did) -- `species` stays an inert empty placeholder (`MaceEncoder` doesn't use `dim_red.soap`'s chemical-species machinery; its checkpoint carries its own supported-species table internally), and `dataset.extxyz` isn't read. `encode_structures`' mace branch calls `MaceEncoder.encode(atoms_list)` directly (raw pooled features) then applies the *same* standardization `load_trained_run` recovered -- unlike cgcnn's raw (never-standardized) graph features, mace embeddings are standardized in the dataset-cache path, so new structures must go through the same standardization to land in a comparable space.
- `pipeline.tail_training.train_tail`'s guard is `model_kind not in ("supcon", "cgcnn", "mace")` -- everything downstream already operates purely on `embeddings.npz` arrays, architecture-agnostic, so no further change was needed there.

See `configs/single_run_mace.example.yaml`.
