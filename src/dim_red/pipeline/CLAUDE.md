# CLAUDE.md

Guidance for `src/dim_red/pipeline/` (moved out of the repo-root `CLAUDE.md` since it's specific to this directory).

**`pipeline.tail_training`** is phase 2 of the SupCon body/tail workflow (see `src/dim_red/supcon/CLAUDE.md`), also reused unmodified to attach a tail on top of an already-completed `model: cgcnn` run's frozen body (see `src/dim_red/cgcnn/CLAUDE.md`) -- everything below operates purely on saved `embeddings.npz` arrays, architecture-agnostic, so nothing here needed to change to support a second body architecture: freezes an already-completed `model: supcon`/`model: cgcnn` run's body and trains exactly one tail (classification or visualization) on top of it — the `dimred-train-tail <config> <run_dir>` console script (`pipeline.cli.train_tail_command`; also reachable as `python -m dim_red.pipeline.cli --train-tail <config> --train-tail-run <run_dir>`), a deliberately separate command/invocation from `dimred-run` so the same trained body can have several different tail configs tried against it without repeating phase-1 contrastive training. The run directory is always a separate CLI argument, not read from the YAML (`pipeline.config.TailTrainConfig.run_dir` is `Optional[str] = None` for exactly this reason) — `_do_train_tail` overrides whatever `run_dir` the config sets (if any) with the CLI-supplied one via `dataclasses.replace`, mirroring `dimred-apply <structures> <run_dir>`'s two-positional-argument shape, so one tail-training config can be reused unedited across many runs; `train_tail` itself raises if `config.run_dir` is still `None` by the time it actually needs it (i.e. when called programmatically without going through the CLI). `train_tail(config: TailTrainConfig)` uses `inference.load_run_embeddings` — a lightweight loader that reads only `config.yaml`/`embeddings.npz` (requires just those two files to exist, not `dataset.extxyz`/`model_params.msgpack`) and never reconstructs the body, resolves species, or computes/recomputes standardization stats, since none of that is needed to train a tail on already-saved representations — deliberately *not* `inference.load_trained_run` (which does all of that, and would trigger its SOAP-recompute fallback for a pre-existing run missing `feature_mean`/`feature_std`, entirely pointlessly here). It then reads `r_train`/`r_val`/label ids directly out of that run's own `embeddings.npz` (via its `split` field) — no SOAP recompute, no body forward pass at all, so this is freely rerunnable, including against a run whose `dataset.extxyz`/`model_params.msgpack` no longer exist. Dispatches to `dim_red.supcon.tail_training.train_classification_tail`/`train_visualization_tail` based on `config.tail_kind`, and writes artifacts to `<run_dir>/tails/<output_subdir or tail_kind>/` (dedup-suffixed like run directories, so repeated invocations don't clobber each other by default) -- created and logged to (`run.log`, same `logging.FileHandler`-attach/`finally`-detach pattern as `single_run.run_single`'s own `run.log`, attached as early as possible so every line from `"Training tail_kind=..."` onward is captured) before anything else: `tail_config.yaml` (records the actual `run_dir` used, for the record), `tail_params.msgpack`, `loss_history.csv`, plus, for a classification tail, `tail_predictions.npz` (soft-masked `family_probs`/`spacegroup_probs` + vocab arrays for every point — the same style of block `run_single` skips for supcon bodies, finally exercised here — plus the true `labels`/`spacegroups`, so this file is self-sufficient for re-evaluating the classifier later without rejoining against the parent run's own `embeddings.npz`) **and** a classifier-evaluation plot suite: a confusion matrix, a per-class precision/recall/F1 bar chart, and a calibration/reliability diagram (`confusion_matrix_<level>_<split>.png`/`classification_report_<level>_<split>.png`/`calibration_<level>_<split>.png`), for every active label level (`family`, and `spacegroup` when that term is active) **and** both the train and val splits (via the same `train_idx`/`val_idx` masks already built for training) — 6 PNGs for `family_only`, 12 for `family_and_spacegroup`. Or, for a visualization tail, `tail_embeddings.npz` plus plot(s) (`viz_plot_family.png`, and `viz_plot_spacegroup.png` when that term is active) — using the tail's own learned projection, not UMAP. Latent-space plots use `analysis.plotting.plot_reduced_space` for `viz_dim: 2` or the new `plot_reduced_space_3d` (matplotlib's built-in `mpl_toolkits.mplot3d`, no new dependency) for `viz_dim: 3`. The three new classifier-evaluation functions (`analysis.plotting.plot_confusion_matrix`/`plot_classification_report`/`plot_reliability_diagram`) are the first use of `sklearn.metrics` (`confusion_matrix`/`accuracy_score`/`classification_report`) anywhere in this codebase -- not a new pip dependency, since scikit-learn is already a base `pyproject.toml` dependency; each decodes predictions via `class_names[y_probs.argmax(axis=1)]` from the same softmax `y_probs` arrays `tail_predictions.npz` already saves, and follows this module's existing style (`plt.figure()`/`plt.savefig()` state calls, manual `ValueError` shape checks) except the confusion matrix intentionally uses a sequential `"Blues"` colormap (it encodes a magnitude/fraction, not class identity) rather than the categorical `tab10` the rest of the module uses. `pipeline.config.TailTrainConfig`/`ClassificationTailConfig`/`VisualizationTailConfig`/`TailTrainSettings` are a fully independent config schema (own YAML shape, own `load_tail_train_config`/`tail_train_config_to_dict`) rather than nested under `RunConfig`, since this targets an already-completed run directory rather than building a dataset from scratch — `ClassificationTailConfig.mode` reuses `AuxHeadsConfig`'s 2-value restriction (`"family_only"`/`"family_and_spacegroup"` — the spacegroup head is family-masked, so an unconditioned `"spacegroup_only"` isn't meaningful), while `VisualizationTailConfig.mode` reuses `SupConConfig`'s full 3-value set (independent terms, no masking) and also carries its own `batching: BatchingConfig`. See `configs/tail_train_classification.example.yaml`/`configs/tail_train_visualization.example.yaml`.

`RunConfig.tails` (`pipeline.config.AutoTailsConfig`, YAML: top-level `tails:` block with `classification`/`visualization`/`train` sub-blocks — same shapes as `TailTrainConfig`'s, reusing `ClassificationTailConfig`/`VisualizationTailConfig`/`TailTrainSettings` directly) lets `dimred-run`/`dimred-sweep` auto-invoke phase 2 right after phase 1, instead of requiring a separate manual `dimred-train-tail` call: `single_run.run_single` calls `pipeline.tail_training.train_tail` itself — the exact same entry point, so identical artifacts/logging — once for `config.tails.classification` and once for `config.tails.visualization` when either is set (both can be set together, training both tails out of one `dimred-run`/`dimred-sweep` invocation), right after the body's `model_params.msgpack`/`projection_params.msgpack` are saved and before the run's final "Run complete" log line. `None` (default) disables it, current behavior unchanged; ignored for `model_kind not in ("supcon", "cgcnn")`, same treatment `aux_heads`/`supcon`/`batching` get for the model kinds they don't apply to. Since `run_sweep` already just calls `run_single` once per grid combination, this reaches every run in a sweep with zero changes to `sweep.py` — a swept `tails.*` dotted path (e.g. `tails.classification.mode`) works for free, same as any other field. A tail-training failure inside this call propagates and aborts the run/sweep immediately (fail-fast, no try/except-and-continue precedent anywhere in `run_sweep`/`run_single`). Because `train_tail` is invoked from inside `run_single`'s own `try` block, while its own `run.log` `FileHandler` is added to the same shared `"dim_red.pipeline"` logger `run_single`'s handler is still attached to, the parent run's `run.log` ends up containing a full trace of any auto-triggered tail training too, in addition to `<run_dir>/tails/<tail_kind>/run.log`. The three shared dict-parsing helpers this reuses (`_parse_classification_tail_config`/`_parse_visualization_tail_config`/`_parse_train_settings`, extracted from what was previously inline-duplicated logic in `tail_train_config_from_dict`) live in `pipeline.config` alongside `run_config_from_dict`/`tail_train_config_from_dict`, both of which now call them. See `configs/single_run_supcon.example.yaml`/`configs/sweep_supcon.example.yaml`'s commented `tails:` block.

**`pipeline.inference`** (SOAP-based model kinds -- `vae`/`autoencoder`/`supcon`; see `src/dim_red/cgcnn/CLAUDE.md` for `model_kind: cgcnn`'s parallel, SOAP-free `_build_model`/`encode_structures` branches) applies an already-trained run's model to new structures (a list of `Atoms` outside the original dataset) and plots them in that run's latent space alongside the original training data — the `dimred-apply <structures.extxyz> <run_dir>` console script (`pipeline.cli.apply_command`; also reachable as `python -m dim_red.pipeline.cli --apply <structures> --apply-run <run_dir>`). `load_trained_run(run_dir)` reads all four artifacts a completed `run_single` run always writes together (`config.yaml`, `dataset.extxyz`, `model_params.msgpack`, `embeddings.npz`); it resolves the species list from `dataset.extxyz` (cheap: just reading back which chemical symbols are present, no SOAP involved) and, for the standardization stats, takes `feature_mean`/`feature_std` **directly from `embeddings.npz`** — saved there by `run_single` since `dataset_cache.build_dataset_for_run`/`get_or_build_dataset`/`get_or_build_pyxtal_dataset` now return them alongside the standardized `features` (`_compute_soap_and_standardize` returns `(X_std, feature_mean, feature_std)` instead of discarding the fit like `dim_red.utils.standardize` does, and they're cached in the dataset-cache `.npz` too, so a sweep's cache-hit runs get them for free) — **no SOAP recomputation on the training set at all**. Runs written before this field existed (`feature_mean`/`feature_std` missing from `embeddings.npz`) fall back to the old behavior: recompute SOAP on `dataset.extxyz` via `fit_standardization`, and cross-check the recomputed standardized features against `embeddings.npz['features']`, logging a warning (not a hard failure) on mismatch (e.g. `config.yaml` hand-edited out of sync with what actually produced the run) — this fallback (and its mismatch check) only run for such pre-existing runs; a run trained after this fix never triggers it. Either way, the model architecture is then rebuilt (reading `n_family_classes`/`n_spacegroup_classes`, for `vae`/`autoencoder`, off `embeddings.npz`'s `family_classes`/`spacegroup_classes` lengths, since `RunConfig` itself doesn't carry the resolved class counts) and its trained weights loaded via `flax.serialization.from_bytes`. `encode_structures` then featurizes/standardizes new structures through that *same* recovered pipeline (not their own independently-fit standardization) so they land in a latent space actually comparable to the training set's — every chemical species in the new structures must be among the recovered species list or SOAP computation raises (this is the one place `load_trained_run`'s pipeline still runs SOAP -- necessarily, since these are structures the model has never seen). `plot_applied_in_latent_space` overlays the new points (as black-edged stars, via `analysis.plotting.plot_applied_structures`) on the run's original dataset; when the latent space isn't already 2D, both are projected into one *shared* 2D space by fitting `dim_red.umap.UMAP` on the original embeddings and then `.transform()`-ing the new points through that same fit (reusing `pipeline.compare.make_umap`/`LatentUmapParams` — renamed public from `compare`'s former `_make_umap` specifically so `inference` could reuse it) rather than two independent fits, which would place old and new points in unrelated coordinate systems. `apply_model_to_structures` is the end-to-end entry point: writes `<stem>_embeddings.npz` (new latent coords + `material_id`s, plus `labels` when `--label-field` names an `atoms.info` key to color points by) and `<stem>_latent_space.png` to `<run_dir>/applied` by default. `utils.fit_standardization`/`apply_standardization` (split out of `utils.standardize`, which is now a thin `fit` + `apply` composition, unchanged behavior) are what both `dataset_cache._compute_soap_and_standardize` and `inference`'s fallback path use to fit/reuse standardization statistics. `load_run_embeddings(run_dir)`/`RunEmbeddings` are a lighter-weight counterpart for callers that only need `config.yaml`/`embeddings.npz` and never the reconstructed model at all — requires just those two files (not the full four), never touches SOAP or `dataset.extxyz`/`model_params.msgpack` in any way; see `pipeline.tail_training` above, its one caller.

**`pipeline.benchmark`** assembles a single wide CSV *quantifying* run quality across `model_kind`s (`vae`/`autoencoder`/`supcon`/`cgcnn` together, unlike `pipeline.compare`, which renders a plot suite for one sweep directory at a time and implicitly assumes comparable `loss_history.csv` columns within it) for the user to read and judge themselves — it never ranks or auto-selects a "best" run/config, deliberately: the only thing it produces is a table — the `dimred-benchmark <input>... --output <csv>` console script (`pipeline.cli.benchmark_command`; also reachable as `python -m dim_red.pipeline.cli --benchmark <input>... --benchmark-output <csv>`), accepting any mix of individual run directories and sweep directories in one call. This exists because raw training loss isn't a valid cross-`model_kind` comparison signal: `loss_history.csv` column names and scales diverge by kind (vae = reconstruction+KL+CE, autoencoder = reconstruction+CE, cgcnn = pure CE, supcon = a contrastive loss with a `_supcon`-suffixed column name instead of `_ce`), so `pipeline.compare.available_loss_metrics`'s column-name intersection collapses to just `train_loss`/`val_loss` once kinds are mixed, and even that pair isn't the same objective across them. `collect_run_dirs(inputs)` resolves each input path: if it's already a completed run (`config.yaml` + `loss_history.csv` directly inside), it's used as-is; otherwise it's expanded via `pipeline.compare.discover_runs` as a sweep directory — deduplicated and sorted.

`benchmark_row(run: RunData, key_hyperparams=...)` builds one row, its two headline quality signals first, in priority order, everything else after for reference: **(1) primary** — every key from `run_classification_accuracies(run)` (crystal-family, and spacegroup when available, classification accuracy) — which tries `pipeline.compare.classification_accuracies_from_npz(run.embeddings)` first (vae/autoencoder/cgcnn's built-in heads), and if that's empty (a supcon body, or any run without `aux_heads`), falls back to `<run_dir>/tails/classification/tail_predictions.npz` if present (a supcon or cgcnn classification tail — same payload key names, so one function reads both sources uniformly); **(2) secondary** — `dim_red.analysis.metrics.embedding_quality_metrics` computed on `_resolve_2d_embedding(run)` (keys prefixed `family_2d`/`spacegroup_2d`) — how well families/phases separate specifically in the 2D view a human would actually look at in a plot, as opposed to whatever the native `latent_dim` happens to be. `_resolve_2d_embedding` picks, in preference order: an already-trained `viz_dim: 2` visualization tail's own embeddings (`<run_dir>/tails/visualization/tail_embeddings.npz` — a genuine learned 2D projection, SupCon loss on the frozen body, not a post-hoc reduction) if its shape is exactly `(n, 2)`; else the run's native `embeddings` directly, if already 2D; else a deterministic PCA projection to 2 components (`dim_red.pca.PCA`, the same wrapper `pipeline.compare` uses for its classical baseline — no extra `umap-learn` dependency); `None` (native embedding has fewer than 2 dimensions) is written as `NaN` across the whole `family_2d`/`spacegroup_2d` column group (`_2D_METRIC_KEYS`), so that group is always present regardless. After those two groups: `run_dir`/`model_kind`/`n_samples`/`wall_clock_seconds` (from `run_wall_clock_seconds`, `run.log`'s own first/last timestamp span, with any nested `tails/<kind>/run.log` span subtracted back out so an auto-tail-trained run's phase-1 time stays comparable to one without), the requested dotted-path `key_hyperparams` (default: `model`, `vae.latent_dim`, `vae.encoder_hidden_dim`, `train.learning_rate`, `train.batch_size`, `train.epochs`, `seed`), every `loss_history.csv` column's final value prefixed `final_` (kept for reference/debugging only — explicitly **not** cross-`model_kind`-comparable, per above), and every key from `embedding_quality_metrics` again, this time on the run's *native*-dimensionality `embeddings` (unprefixed `family`/`spacegroup` keys — present unconditionally for every `model_kind`, regardless of `latent_dim` or whether that kind has classifier heads at all).

`generate_benchmark_table` writes one row per resolved run to `output_csv` via `pipeline.compare.write_csv` (promoted public from that module's former `_write_csv`, alongside `_aux_accuracies` → `classification_accuracies_from_npz`, also promoted public and generalized from `RunData` to a plain npz-shaped dict so both storage locations above can share it), fieldnames the union of every row's keys in first-seen order (a run missing some column, e.g. no spacegroup variety or no classifier at all, gets an empty cell there rather than the whole table failing to build). `dim_red.analysis.metrics.embedding_quality_metrics(embeddings, label_sets, *, knn_k=5, knn_cv_folds=5, kmeans_seed=0)` is the standalone, `sklearn`-only scoring function behind both column groups above (no `RunConfig`/`RunData` dependency, importable on its own) — for each named label array in `label_sets` (rows with a negative/sentinel label excluded from that name's scores only), reports `f"{name}_silhouette"`/`f"{name}_kmeans_ari"`/`f"{name}_kmeans_nmi"`/`f"{name}_knn_accuracy"`; a label set with fewer than 2 valid classes, or a class smaller than the requested CV folds, gets `NaN` for its metrics (logged, not raised) rather than aborting the whole call, since a benchmark table walking many runs shouldn't abort on one under-populated label set. See `configs/benchmark_pyxtal_base.example.yaml` and `configs/tuning_sweep_{vae,autoencoder,supcon,cgcnn}.example.yaml` for a full two-stage (within-kind tuning, then cross-kind benchmark) playbook built on top of this and `dimred-sweep`.

See the repo-root `CLAUDE.md` for the Optimizer-selection and Early-stopping conventions, which `pipeline.single_run`/`pipeline.tail_training` read config for (`TrainSettings.optimizer`/`TailTrainSettings.optimizer`, `EarlyStoppingConfig`), `src/dim_red/supcon/CLAUDE.md` for the phase 1/2 body-and-tail workflow this all sits on top of, and `src/dim_red/cgcnn/CLAUDE.md` for the graph-convolutional body `pipeline.single_run`/`pipeline.dataset_cache`/`pipeline.inference` each grow a parallel branch for.
