## Architecture

`src/dim_red/` is a materials-science dimensionality-reduction toolkit with two independent verticals joined by an analysis workflow:

- **Data ingestion** (`fetch.py`): pulls crystal structures from the Materials Project API (`mp_api`) filtered by crystal system, converts pymatgen `Structure` objects to ASE `Atoms` via `AseAtomsAdaptor`, and stashes the `material_id` on `atoms.info`.
- **`augmentation.py`**: diversifies a fetched (or generated) structure database via data augmentation — `augment_structures`/`AugmentationConfig` apply configurable-probability positional jitter (simulated thermal noise: small Gaussian displacements of every atom) and/or vacancy (random atom removal) to each structure, producing `n_augmented` tagged copies per input (`fetch_and_augment_structures` chains this right after `fetch_structures_by_crystal_system`). `_augment_once` guarantees every augmented copy has at least one of jitter/vacancy actually applied to it (independent probability rolls for each; if *neither* succeeds, one is forced on rather than the copy coming out identical to the original) — the corollary being that if only one mechanism is configured at all (`jitter_std > 0` xor `vacancy_atom_probability > 0`), that one applies to every augmented copy regardless of its own probability, since it's the only thing that can be forced. Vacancy removal is capped by `max_vacancies` (`None` default = uncapped) rather than a minimum-atoms floor — it always keeps at least 1 atom regardless of that cap, but doesn't otherwise guarantee a minimum count. If `AugmentationConfig.supercell_radius` is set, `augment_structures` first runs every input structure through `make_supercell_for_radius` (once per structure, before building the kept-original copy and any augmented ones) -- repeats the cell an integer number of times along each periodic lattice vector so a sphere of that radius (Angstroms) fits inside without touching its own periodic image (the standard "perpendicular cell width >= 2 * radius" sizing rule, computed independently per axis off the *original* unrepeated cell since repeating other axes doesn't change a given axis's perpendicular width). Meant for unit cells too small to meaningfully augment -- pyxtal can generate cells holding as few as 1-2 atoms -- `None` (default) skips this step, current behavior unchanged. Wired into the pipeline via `RunConfig.augmentation` (YAML: top-level `augmentation:` block, `pipeline.config.AugmentationConfig` -- kept as its own dataclass mirroring `dim_red.augmentation.AugmentationConfig` one-to-one, same reasoning as `PyxtalConfig` mirroring `GenerationConfig`, so `pipeline.config` doesn't pull in `dim_red.augmentation`'s import chain, i.e. `dim_red.fetch` -> `mp_api`/`pymatgen`, just to parse a config); `None` (default) disables it, current behavior unchanged. `pipeline.dataset_cache.build_dataset_for_run`'s `_resolve_augmentation` converts it to the real `dim_red.augmentation.AugmentationConfig` and resolves `seed` the same way `PyxtalConfig.seed` does (falls back to `RunConfig.seed` when unset), then both `get_or_build_dataset`/`get_or_build_pyxtal_dataset` run `augment_structures` on the fetched/generated structures right before SOAP -- applies regardless of `data_source`. The augmentation settings are folded into the dataset cache key, so a config that changes only `augmentation` doesn't reuse a cache built without it (or with different settings).
- **Featurization** (`soap.py`): computes SOAP (Smooth Overlap of Atomic Positions) descriptors from `Atoms` objects using `dscribe`. Has an optional `normalize_distances` preprocessing step that rescales atomic positions so the nearest-neighbor distance is 1.0, making descriptors invariant to absolute bond-length scale.
- **Classical dimensionality reduction** (`pca.py`, `umap.py`, `utils.py`): thin, fit/transform-style wrapper classes around scikit-learn's `PCA` and `umap-learn`'s `UMAP`, both validating `n_components` and raising if used before fitting. `UMAP.__init__` also takes optional `n_neighbors`/`min_dist`/`metric`/`random_state`, each `None` by default -- left unset, that hyperparameter is whatever `umap-learn` itself defaults to (rather than this wrapper re-picking its own defaults), and only the ones actually given get forwarded to the underlying `SklearnUMAP`. `utils.standardize` does z-score normalization and is the shared preprocessing step before either reduction.
- **`analysis/`**: glues the above into an end-to-end pipeline. `workflow.run_pca_reduction` fetches structures per crystal system → computes SOAP vectors (species auto-detected across all fetched structures) → standardizes → PCA-reduces, returning `(X_reduced, labels, material_ids)`. `plotting.plot_reduced_space` renders a 2D scatter colored by label; `plotting.plot_spacegroup_histogram` renders a spacegroup-count bar chart colored by crystal family. `examples/run_analysis_demo.py` shows the intended top-level usage.
- **`generate.py`**: an alternative to `fetch.py` for building a structure database — generates synthetic, symmetry-valid structures from scratch with `pyxtal` (`GenerationConfig`/`generate_structures`) instead of querying Materials Project, returning the same `List[Atoms]` shape (`info["material_id"]`/`info["spacegroup"]`, plus `info["family"]`) so it's a drop-in alternative downstream. Configurable per-space-group or per-family (with uniform/random splitting across a family's space groups) structure counts, and how many chemical species per structure (which elements doesn't matter — sampled from a placeholder pool). Logs a warning for any space group whose Wyckoff multiplicities couldn't accommodate the requested structures. Not a hard dim_red dependency — requires `pip install pyxtal`. See `examples/pyxtal_structure_generation.ipynb` for a guided walkthrough, and `pipeline/dataset_cache.py`'s `RunConfig.data_source == "pyxtal"` for its pipeline integration: `RunConfig.fetch`/`RunConfig.pyxtal` are symmetric, data-source-specific config blocks (`pipeline/config.py`'s `FetchConfig`/`PyxtalConfig`), exactly one of which must be set matching `data_source` (YAML: `fetch:`/`pyxtal:` top-level blocks — `crystal_systems`/`limit_per_system`/`api_key` now live under `fetch:`, not a flat top level).
- **`vae/`**: a separate, JAX/Flax-based neural dimensionality reduction path, independent of the PCA/UMAP/SOAP pipeline (it operates on arbitrary feature matrices via `VAEDatabase`, not specifically SOAP output):
  - `model.py`: `VAEModule` (Flax `nn.Module`) composing `EncoderModule`/`DecoderModule` MLPs with configurable hidden-layer sequences; `VAE` is the high-level wrapper holding `params` and exposing `encode`/`decode`/`forward` plus `*_with_params` variants for use inside jitted training steps. Decoder hidden dims default to the mirror (reverse) of the encoder's unless `mirror=False`.
  - `codec.py`: `split_encoder_decoder` produces standalone `VAEEncoder`/`VAEDecoder` callables from a trained `VAE` for downstream use without exposing the full model.
  - `database.py`: `VAEDatabase` wraps a `(n_samples, n_features)` array and provides a reproducible `train_val_split`.
  - `training.py`: `train_vae` runs a full train/val loop using `learned_optimization`'s VeLO meta-learned optimizer (via `prefab.optax_lopt`) as the optimizer backend — note `TrainConfig.learning_rate` is unused by VeLO and kept only for API compatibility. Batches are jitted with `jax.jit`/`jax.vmap`; validation batches are padded to a fixed size with a mask so `vmap` can process a whole epoch in one call. `TrainConfig.device` selects the JAX backend (`"cpu"`/`"gpu"`) and training raises if no matching JAX device exists.
- **`autoencoder/`**: a deterministic (non-variational) counterpart to `vae/`, mirroring its exact module layout and public API shape (`model.py`'s `Autoencoder`/`Encoder`/`Decoder`, `codec.py`'s `split_encoder_decoder`, `training.py`'s `TrainConfig`/`train_autoencoder`) so the two are interchangeable. The only real difference: `Autoencoder.encode` returns a single deterministic `z` (not a sampled `(mu, logvar)` posterior), so there's no KL term, no `beta`, and no PRNG key needed at encode/decode/forward time. Reuses `vae.database.VAEDatabase` directly (dataset handling has nothing model-specific about it) rather than duplicating it. `pipeline.single_run.run_single` picks between `vae`/`autoencoder` via `RunConfig.model_kind` (YAML: top-level `model: vae` or `model: autoencoder`, default `vae`); both read architecture from the same `vae:` config block and aux-heads from the same `aux_heads:` block, so a sweep can vary `model` like any other grid axis (see `configs/single_run_autoencoder.example.yaml`).
- **`supcon/`**: an encoder-only counterpart to `vae/`/`autoencoder/` — no decoder, no reconstruction loss, no KL/`beta` at all. Structured as a **body** (`SupConEncoder`, producing a representation `r`) plus, at any given moment, exactly **one attachable tail** (`tails.py`), loosely following Khosla et al. 2020's SupCon recipe generalized to three tail kinds: a `ProjectionTail` attached during the body's own (only) training stage, and a `ClassificationTail`/`VisualizationTail` attachable afterwards, one at a time, once the body is frozen.
  - `model.py`: `EncoderModule` (Flax `nn.Module`, deliberately duplicated from `autoencoder.model.EncoderModule` rather than imported, so this package stays independent of `vae`/`autoencoder`) plus `SupConEncoder`, the high-level wrapper (`params`, `encode`/`encode_with_params`) — the body. Unmodified by the tail architecture below: still no `Decoder`, no classifier heads, no `codec.py` baked into it — tails are always separate Flax modules with their own independently-initialized `params` pytrees, never nested inside the body's.
  - `tails.py`: `ProjectionTail`/`VisualizationTail` (small MLPs, `r -> R^d`, sharing a private `_MLPTail` Flax module — structurally and loss-identical, differing only in output width and which stage attaches them) and `ClassificationTail` (`ClassifierHead`/`apply_family_mask`, verbatim duplicates of `vae.model`'s, plus a `ClassificationTailModule` mirroring `VAEModule`'s head setup minus the encoder/decoder it also owns). Every tail's `params` is a wholly separate pytree from the body's `SupConEncoder.params` — never a sub-tree reached by traversing it — which is what lets phase 1 (below) compose them as two independently-keyed dict branches (`{"body": ..., "tail": ...}`) and what lets phase 2 simply omit the body's pytree from that dict entirely to "freeze" it, with no `jax.lax.stop_gradient`/`optax.multi_transform`/masked-optimizer machinery needed anywhere (there is no other freezing precedent in this codebase).
  - `training.py` (**phase 1**): `TrainConfig` (`epochs`/`batch_size`/`learning_rate` — unused, VeLO again — /`tau`/`seed`/`device`; deliberately *without* `lambda_family`/`lambda_spacegroup`/`lambda_norm`, which live in `pipeline.config.SupConConfig` instead and are passed to `train_supcon` as explicit arguments — none of the three are training-loop mechanics like `tau`, they're loss-term weights). `train_supcon(model, projection_tail, train_db, val_db, config, ...)` jointly trains the body and a `ProjectionTail` — `params` is `{"body": model.params, "tail": projection_tail.params}`, one `jax.value_and_grad` differentiates both at once, and both are written back (`model.params`/`projection_tail.params`) at the end. `supcon_loss(z, labels, tau)` implements Supervised Contrastive (Khosla et al. 2020) with a *negative squared-Euclidean-distance* similarity (`-||z_i - z_j||^2 / tau`, not the more common cosine-similarity formulation — no internal L2-normalization of `z`), and for each anchor sums over same-label positives in the batch (self excluded) normalized by a log-sum-exp over every other batch row. An anchor with no positive in its batch is excluded from that term's mean (not zeroed-and-diluted) — implemented by dividing by the count of anchors that *did* have a positive, not the batch size. A large finite negative sentinel (not `-jnp.inf`) masks self-comparisons before `log_softmax`, since `0 * -inf` is NaN in the forward pass, not just the gradient — a real pitfall if you touch this function. Crucially, `supcon_loss`/`norm_penalty` are computed on **the projection tail's output `z = Proj(r)`, not the body's own representation `r`** (Khosla et al. 2020's actual recipe) — pure functions over any latent batch, so this is just a matter of which tensor `_make_train_step`/`_make_eval_step` feed them, and `lambda_norm`'s regularization target moves with it. `norm_penalty(z)` (`mean(sum(z**2, axis=-1))`) is available as an optional regularizer, weighted by `lambda_norm` (`0.0` — disabled — by default, unlike `lambda_family`/`lambda_spacegroup` not gated by `mode` since it doesn't depend on labels at all) and added to `total` in both `_make_train_step`/`_make_eval_step` identically, so `val_loss` reflects the same objective actually optimized; `train_norm_penalty`/`val_norm_penalty` are always in `history`, regardless of `lambda_norm`, for diagnosing unbounded embedding growth even when the penalty itself is off. `train_supcon` mirrors `train_vae`/`train_autoencoder`'s `has_family`/`has_spacegroup` compile-time-branch pattern and VeLO optimizer setup, but deliberately does **not** reuse their padding+`vmap`-over-epoch validation trick: SupCon is pairwise *within* a batch, so a zero-padded dummy row would become a spurious positive/negative for real rows (unlike MSE/cross-entropy, computed independently per row). Both train and validation instead use a plain unpadded batch loop (one jitted call per batch), epoch metrics combined as a batch-size-weighted mean.
  - `tail_training.py` (**phase 2**): `TailTrainConfig` (training-loop mechanics only — mirrors `training.TrainConfig`'s shape) plus `train_classification_tail`/`train_visualization_tail`, each training exactly one tail against a **frozen body's already-computed representations**, passed in directly as plain `r_train`/`r_val` arrays (not a `VAEDatabase` — these are fixed representations to train a small head on, not raw features to standardize/encode, and there's no body forward pass at all in either loop, hence no `SupConEncoder` argument here). `train_classification_tail` mirrors `autoencoder.training`'s aux-head cross-entropy/`apply_family_mask` shape; `train_visualization_tail` reuses `supcon_loss`/`norm_penalty` directly from `training.py` (genuinely shared pure math, not duplicated) computed on the visualization tail's own output, and supports the same `"random"`/`"balanced"` batching choice as phase 1 (via `sampling.iter_balanced_batches`). `_iter_batches`/`_weighted_mean` are duplicated here (matching the existing `_iter_batches` duplication precedent between `autoencoder.training`/`supcon.training`). See `dim_red.pipeline.tail_training` below for the end-to-end entry point that supplies `r_train`/`r_val` from a completed run's `embeddings.npz`.
  - `sampling.py`: an alternative to plain random shuffling for *training* batches only (validation batches always stay random, regardless), selected via `BatchingConfig.strategy == "balanced"` (`pipeline.config`) — used by both phase 1's `train_supcon` and phase 2's `train_visualization_tail`. `iter_balanced_batches`/`balanced_batch_indices` build each batch as `P` families x `K` examples per family, always further stratified across spacegroups within each family, `K // S_eff` examples each — the remainder `K % S_eff` going to the first few chosen spacegroups when it doesn't divide evenly. `S` (`BalancedBatchingParams.S`) picks how many spacegroups per family: `None` (default) uses *every* spacegroup present for that family (`S_eff = n_spacegroups_present`), an explicit integer samples only that many (clamped down, with a `logger.warning`, if it exceeds what's present) — so the SupCon loss reliably has positives available for every anchor even on less-balanced datasets, and by default batches are as evenly spread across a family's spacegroups as `K` allows. `P` is clamped the same way. Because spacegroup stratification is always applied now, `spacegroup_ids` is a required argument to both functions (not optional) — callers always build spacegroup ids whenever `batching.strategy == "balanced"`, regardless of the active loss `mode`/`S`. Row sampling is without replacement when the pool is large enough, with replacement only when necessary (a small family/spacegroup). Uses `logging.getLogger("dim_red.pipeline")` — the same logger name every other pipeline module uses, not a `dim_red.supcon`-prefixed one — purely so these warnings land in a run's `run.log` (a plain `logging` name, not an import, so this doesn't create a dependency on `dim_red.pipeline`).
  - Phase 1 reuses `vae.database.VAEDatabase` directly, same as `autoencoder` (phase 2 doesn't — see `tail_training.py` above).
  - `pipeline.single_run.run_single` integrates `model_kind == "supcon"` as a third branch alongside `vae`/`autoencoder` (model + `ProjectionTail` construction, `train_config`, the training call, and `_log_epoch`'s per-history-key logging), all additive — the `vae`/`autoencoder` branches are untouched. It reads its encoder architecture from the same `vae:` block (`decoder_hidden_dim`/`mirror` ignored, like `autoencoder` ignores `beta`) but its own `supcon:` block (YAML: `mode` — `"family_only"`/`"spacegroup_only"`/`"family_and_spacegroup"`, mirroring `aux_heads.mode`'s shape but independent per term, since there's no family→spacegroup masking to require family whenever spacegroup is active — plus `lambda_family`/`lambda_spacegroup`/`tau`/`lambda_norm`/`projection_dim` (Khosla et al. 2020 default `128`, the projection tail's output width, separate from `vae.latent_dim`)/`projection_hidden_dim` (`None` -> one hidden layer matching `vae.latent_dim`)) instead of `aux_heads:`, and its batch-sampling strategy from `batching:` (`pipeline.config.BatchingConfig` — `strategy: random` (default) or `balanced`, plus `balanced_params: {P, K, S}`; ignored for `vae`/`autoencoder`, which always shuffle). The trained `ProjectionTail`'s params are saved to a 5th run artifact, `projection_params.msgpack` (discarded after phase 1 in the original paper; kept here for reproducibility, though nothing downstream ever reloads it — `inference.load_trained_run`'s required-file set stays at 4 entries). Since the body itself still has no classifier heads, `run_single`'s family/spacegroup-probability inference block is still skipped entirely for this `model_kind`; `embeddings.npz`'s `embeddings` field is still the body's raw `r` (unchanged by any of this — the projection tail's output never gets saved there), and the file keeps only the base fields (`embeddings`/`features`/`labels`/`material_ids`/`spacegroups`/`split`), no `*_probs`/`*_classes`. Note `train_supcon`'s `train_family_ids`/`train_spacegroup_ids` (which family/spacegroup terms the *loss* uses) are deliberately independent of its `batching_family_ids`/`batching_spacegroup_ids` (which labels *batches* are grouped by) — `run_single` builds family/spacegroup vocab ids whenever either is needed, so e.g. `supcon.mode: spacegroup_only` + `batching.strategy: balanced` still groups batches by family even though the family loss term itself stays inactive. See `configs/single_run_supcon.example.yaml`/`configs/sweep_supcon.example.yaml`.

**`pipeline.tail_training`** is phase 2 of the SupCon body/tail workflow (see `supcon/` above): freezes an already-completed `model: supcon` run's body and trains exactly one tail (classification or visualization) on top of it — the `dimred-train-tail <config> <run_dir>` console script (`pipeline.cli.train_tail_command`; also reachable as `python -m dim_red.pipeline.cli --train-tail <config> --train-tail-run <run_dir>`), a deliberately separate command/invocation from `dimred-run` so the same trained body can have several different tail configs tried against it without repeating phase-1 contrastive training. The run directory is always a separate CLI argument, not read from the YAML (`pipeline.config.TailTrainConfig.run_dir` is `Optional[str] = None` for exactly this reason) — `_do_train_tail` overrides whatever `run_dir` the config sets (if any) with the CLI-supplied one via `dataclasses.replace`, mirroring `dimred-apply <structures> <run_dir>`'s two-positional-argument shape, so one tail-training config can be reused unedited across many runs; `train_tail` itself raises if `config.run_dir` is still `None` by the time it actually needs it (i.e. when called programmatically without going through the CLI). `train_tail(config: TailTrainConfig)` uses `inference.load_run_embeddings` — a lightweight loader that reads only `config.yaml`/`embeddings.npz` (requires just those two files to exist, not `dataset.extxyz`/`model_params.msgpack`) and never reconstructs the body, resolves species, or computes/recomputes standardization stats, since none of that is needed to train a tail on already-saved representations — deliberately *not* `inference.load_trained_run` (which does all of that, and would trigger its SOAP-recompute fallback for a pre-existing run missing `feature_mean`/`feature_std`, entirely pointlessly here). It then reads `r_train`/`r_val`/label ids directly out of that run's own `embeddings.npz` (via its `split` field) — no SOAP recompute, no body forward pass at all, so this is freely rerunnable, including against a run whose `dataset.extxyz`/`model_params.msgpack` no longer exist. Dispatches to `dim_red.supcon.tail_training.train_classification_tail`/`train_visualization_tail` based on `config.tail_kind`, and writes artifacts to `<run_dir>/tails/<output_subdir or tail_kind>/` (dedup-suffixed like run directories, so repeated invocations don't clobber each other by default) -- created and logged to (`run.log`, same `logging.FileHandler`-attach/`finally`-detach pattern as `single_run.run_single`'s own `run.log`, attached as early as possible so every line from `"Training tail_kind=..."` onward is captured) before anything else: `tail_config.yaml` (records the actual `run_dir` used, for the record), `tail_params.msgpack`, `loss_history.csv`, plus, for a classification tail, `tail_predictions.npz` (soft-masked `family_probs`/`spacegroup_probs` + vocab arrays for every point — the same style of block `run_single` skips for supcon bodies, finally exercised here — plus the true `labels`/`spacegroups`, so this file is self-sufficient for re-evaluating the classifier later without rejoining against the parent run's own `embeddings.npz`) **and** a classifier-evaluation plot suite: a confusion matrix, a per-class precision/recall/F1 bar chart, and a calibration/reliability diagram (`confusion_matrix_<level>_<split>.png`/`classification_report_<level>_<split>.png`/`calibration_<level>_<split>.png`), for every active label level (`family`, and `spacegroup` when that term is active) **and** both the train and val splits (via the same `train_idx`/`val_idx` masks already built for training) — 6 PNGs for `family_only`, 12 for `family_and_spacegroup`. Or, for a visualization tail, `tail_embeddings.npz` plus plot(s) (`viz_plot_family.png`, and `viz_plot_spacegroup.png` when that term is active) — using the tail's own learned projection, not UMAP. Latent-space plots use `analysis.plotting.plot_reduced_space` for `viz_dim: 2` or the new `plot_reduced_space_3d` (matplotlib's built-in `mpl_toolkits.mplot3d`, no new dependency) for `viz_dim: 3`. The three new classifier-evaluation functions (`analysis.plotting.plot_confusion_matrix`/`plot_classification_report`/`plot_reliability_diagram`) are the first use of `sklearn.metrics` (`confusion_matrix`/`accuracy_score`/`classification_report`) anywhere in this codebase -- not a new pip dependency, since scikit-learn is already a base `pyproject.toml` dependency; each decodes predictions via `class_names[y_probs.argmax(axis=1)]` from the same softmax `y_probs` arrays `tail_predictions.npz` already saves, and follows this module's existing style (`plt.figure()`/`plt.savefig()` state calls, manual `ValueError` shape checks) except the confusion matrix intentionally uses a sequential `"Blues"` colormap (it encodes a magnitude/fraction, not class identity) rather than the categorical `tab10` the rest of the module uses. `pipeline.config.TailTrainConfig`/`ClassificationTailConfig`/`VisualizationTailConfig`/`TailTrainSettings` are a fully independent config schema (own YAML shape, own `load_tail_train_config`/`tail_train_config_to_dict`) rather than nested under `RunConfig`, since this targets an already-completed run directory rather than building a dataset from scratch — `ClassificationTailConfig.mode` reuses `AuxHeadsConfig`'s 2-value restriction (`"family_only"`/`"family_and_spacegroup"` — the spacegroup head is family-masked, so an unconditioned `"spacegroup_only"` isn't meaningful), while `VisualizationTailConfig.mode` reuses `SupConConfig`'s full 3-value set (independent terms, no masking) and also carries its own `batching: BatchingConfig`. See `configs/tail_train_classification.example.yaml`/`configs/tail_train_visualization.example.yaml`.

`RunConfig.tails` (`pipeline.config.AutoTailsConfig`, YAML: top-level `tails:` block with `classification`/`visualization`/`train` sub-blocks — same shapes as `TailTrainConfig`'s, reusing `ClassificationTailConfig`/`VisualizationTailConfig`/`TailTrainSettings` directly) lets `dimred-run`/`dimred-sweep` auto-invoke phase 2 right after phase 1, instead of requiring a separate manual `dimred-train-tail` call: `single_run.run_single` calls `pipeline.tail_training.train_tail` itself — the exact same entry point, so identical artifacts/logging — once for `config.tails.classification` and once for `config.tails.visualization` when either is set (both can be set together, training both tails out of one `dimred-run`/`dimred-sweep` invocation), right after the body's `model_params.msgpack`/`projection_params.msgpack` are saved and before the run's final "Run complete" log line. `None` (default) disables it, current behavior unchanged; ignored for `model_kind != "supcon"`, same treatment `aux_heads`/`supcon`/`batching` get for the model kinds they don't apply to. Since `run_sweep` already just calls `run_single` once per grid combination, this reaches every run in a sweep with zero changes to `sweep.py` — a swept `tails.*` dotted path (e.g. `tails.classification.mode`) works for free, same as any other field. A tail-training failure inside this call propagates and aborts the run/sweep immediately (fail-fast, no try/except-and-continue precedent anywhere in `run_sweep`/`run_single`). Because `train_tail` is invoked from inside `run_single`'s own `try` block, while its own `run.log` `FileHandler` is added to the same shared `"dim_red.pipeline"` logger `run_single`'s handler is still attached to, the parent run's `run.log` ends up containing a full trace of any auto-triggered tail training too, in addition to `<run_dir>/tails/<tail_kind>/run.log`. The three shared dict-parsing helpers this reuses (`_parse_classification_tail_config`/`_parse_visualization_tail_config`/`_parse_train_settings`, extracted from what was previously inline-duplicated logic in `tail_train_config_from_dict`) live in `pipeline.config` alongside `run_config_from_dict`/`tail_train_config_from_dict`, both of which now call them. See `configs/single_run_supcon.example.yaml`/`configs/sweep_supcon.example.yaml`'s commented `tails:` block.

**Optimizer selection** is implemented identically (duplicated `_make_optimizer(optimizer, learning_rate, num_steps)` helper, same field names, same semantics) in all four training-loop modules (`vae.training`, `autoencoder.training`, `supcon.training` (phase 1, body+projection tail), `supcon.tail_training` (phase 2, both `train_classification_tail`/`train_visualization_tail`)), via each module's own `TrainConfig`/`TailTrainConfig.optimizer` field: `"adam"` (default) builds a plain `optax.adam(learning_rate)`, wrapped in `optax.with_extra_args_support` so it still accepts the `extra_args={"loss": ...}` kwarg every `_make_train_step`/`_make_eval_step` always passes to `tx.update` (VeLO is loss-conditioned; a bare `optax.adam` doesn't accept `extra_args` at all -- this wrapping is what lets every train/eval step's code stay completely unchanged regardless of which optimizer is active); `"velo"` builds `learned_optimization`'s pretrained VeLO meta-learned optimizer via `prefab.optax_lopt(num_steps=...)`, unchanged from this codebase's original (and, before this feature, only) behavior. `"adam"` became the default because VeLO's setup -- importing `learned_optimization`, then loading its pretrained hypernetwork checkpoint -- costs several fixed seconds at minimum before any training starts, and on some networks additionally attempts to resolve Google Cloud credentials in a way that can hang far longer if that path is slow/unreachable rather than failing instantly; this cost is fixed per training call regardless of problem size, so it's proportionally worst for phase-2 tail training (tiny single-hidden-layer MLPs, where a meta-learned optimizer buys nothing). `learning_rate` (already a pre-existing field in every one of these `TrainConfig`s, previously documented as merely "kept for API compatibility") is now Adam's actual learning rate whenever `optimizer == "adam"`; it stays unused when `optimizer == "velo"`. `pipeline.config.TrainSettings.optimizer`/`TailTrainSettings.optimizer` (both `"adam"` default, both validated in `__post_init__` against a shared `_OPTIMIZER_KINDS = ("adam", "velo")` tuple) are the single config-layer fields `pipeline.single_run.run_single`/`pipeline.tail_training.train_tail` read to populate whichever `TrainConfig`/`TailTrainConfig` the active `model_kind`/`tail_kind` uses, and both log it (`optimizer=%s`) alongside their other training-start log lines. **This is a deliberate default-behavior change**: any pre-existing config that doesn't set `train.optimizer` explicitly now trains with Adam instead of VeLO -- set `train.optimizer: velo` to opt back into the original behavior.

**Early stopping** is implemented identically (duplicated code, same field names, same semantics) in all three training loops (`vae.training.train_vae`, `autoencoder.training.train_autoencoder`, `supcon.training.train_supcon`), via four `TrainConfig` fields: `early_stopping` (bool, default `False`), `early_stopping_patience`, `early_stopping_min_delta`, `early_stopping_restore_best`. It always monitors `val_loss` (the full weighted objective each history dict already always has) — not configurable to a different metric in this first pass. Mechanism: after each epoch, if `val_loss < best_val_loss - min_delta` the counter resets (and, if `restore_best_weights`, that epoch's `params` are snapshotted by reference — cheap, since `optax.apply_updates` returns a fresh pytree each step rather than mutating in place); otherwise the counter increments, and once it reaches `patience` the epoch loop `break`s. `model.params` is set to the snapshotted best params at the end when `restore_best_weights` is True (regardless of whether the loop broke early or ran to `epochs`), otherwise to the last epoch's. Returned `history` dicts are simply shorter than `config.epochs` when stopped early — `_save_loss_history` (CSV writer) already derives its row count from the history dict itself, but `pipeline.single_run.run_single`'s per-epoch console/`run.log` logging loop must use `len(history["train_loss"])`, not `config.train.epochs`, or it would index past the end. `pipeline.config.EarlyStoppingConfig` (YAML: `train.early_stopping: {enabled, patience, min_delta, restore_best_weights}`, nested under the existing `train:` block since it's training-loop mechanics like `epochs`/`batch_size`) is the single config-layer source `run_single` reads to populate whichever `TrainConfig` the active `model_kind` uses — default `enabled: false` keeps every pre-existing config backward compatible. `total_steps` for VeLO's `prefab.optax_lopt(num_steps=...)` is still computed from the *configured* `epochs` (not adjusted for early stopping) since it's just a progress-normalization signal for VeLO's learned schedule, not a hard requirement to reach. Caveat for `pipeline.compare`: its "final metric" plots/CSVs read `loss_history[metric][-1]` (the last *logged* epoch) unchanged -- with `restore_best_weights=True` that can be a worse value than what the actually-restored `model.params` achieved a few epochs earlier, since the CSV still records every epoch including the non-improving ones that triggered the stop.

**`pipeline.inference`** applies an already-trained run's model to new structures (a list of `Atoms` outside the original dataset) and plots them in that run's latent space alongside the original training data — the `dimred-apply <structures.extxyz> <run_dir>` console script (`pipeline.cli.apply_command`; also reachable as `python -m dim_red.pipeline.cli --apply <structures> --apply-run <run_dir>`). `load_trained_run(run_dir)` reads all four artifacts a completed `run_single` run always writes together (`config.yaml`, `dataset.extxyz`, `model_params.msgpack`, `embeddings.npz`); it resolves the species list from `dataset.extxyz` (cheap: just reading back which chemical symbols are present, no SOAP involved) and, for the standardization stats, takes `feature_mean`/`feature_std` **directly from `embeddings.npz`** — saved there by `run_single` since `dataset_cache.build_dataset_for_run`/`get_or_build_dataset`/`get_or_build_pyxtal_dataset` now return them alongside the standardized `features` (`_compute_soap_and_standardize` returns `(X_std, feature_mean, feature_std)` instead of discarding the fit like `dim_red.utils.standardize` does, and they're cached in the dataset-cache `.npz` too, so a sweep's cache-hit runs get them for free) — **no SOAP recomputation on the training set at all**. Runs written before this field existed (`feature_mean`/`feature_std` missing from `embeddings.npz`) fall back to the old behavior: recompute SOAP on `dataset.extxyz` via `fit_standardization`, and cross-check the recomputed standardized features against `embeddings.npz['features']`, logging a warning (not a hard failure) on mismatch (e.g. `config.yaml` hand-edited out of sync with what actually produced the run) — this fallback (and its mismatch check) only run for such pre-existing runs; a run trained after this fix never triggers it. Either way, the model architecture is then rebuilt (reading `n_family_classes`/`n_spacegroup_classes`, for `vae`/`autoencoder`, off `embeddings.npz`'s `family_classes`/`spacegroup_classes` lengths, since `RunConfig` itself doesn't carry the resolved class counts) and its trained weights loaded via `flax.serialization.from_bytes`. `encode_structures` then featurizes/standardizes new structures through that *same* recovered pipeline (not their own independently-fit standardization) so they land in a latent space actually comparable to the training set's — every chemical species in the new structures must be among the recovered species list or SOAP computation raises (this is the one place `load_trained_run`'s pipeline still runs SOAP -- necessarily, since these are structures the model has never seen). `plot_applied_in_latent_space` overlays the new points (as black-edged stars, via `analysis.plotting.plot_applied_structures`) on the run's original dataset; when the latent space isn't already 2D, both are projected into one *shared* 2D space by fitting `dim_red.umap.UMAP` on the original embeddings and then `.transform()`-ing the new points through that same fit (reusing `pipeline.compare.make_umap`/`LatentUmapParams` — renamed public from `compare`'s former `_make_umap` specifically so `inference` could reuse it) rather than two independent fits, which would place old and new points in unrelated coordinate systems. `apply_model_to_structures` is the end-to-end entry point: writes `<stem>_embeddings.npz` (new latent coords + `material_id`s, plus `labels` when `--label-field` names an `atoms.info` key to color points by) and `<stem>_latent_space.png` to `<run_dir>/applied` by default. `utils.fit_standardization`/`apply_standardization` (split out of `utils.standardize`, which is now a thin `fit` + `apply` composition, unchanged behavior) are what both `dataset_cache._compute_soap_and_standardize` and `inference`'s fallback path use to fit/reuse standardization statistics. `load_run_embeddings(run_dir)`/`RunEmbeddings` are a lighter-weight counterpart for callers that only need `config.yaml`/`embeddings.npz` and never the reconstructed model at all — requires just those two files (not the full four), never touches SOAP or `dataset.extxyz`/`model_params.msgpack` in any way; see `pipeline.tail_training` below, its one caller.

`dim_red/__init__.py` lazily imports `soap`, `fetch`, `analysis`, `vae`, `autoencoder`, and `supcon` via module-level `__getattr__` (PEP 562) so that importing the base package doesn't require optional heavy dependencies (dscribe, mp_api, jax, flax, etc.) unless those submodules are actually used. `vae/__init__.py`, `autoencoder/__init__.py`, and `supcon/__init__.py` do the same lazy pattern internally for their own symbols. When adding new public symbols to any of these packages, follow this lazy-import pattern rather than importing eagerly at module top.
