## Environment

This project must be run inside the conda environment `dmred` (located at `/home/seraftu/miniconda3/envs/dmred`). In a persistent terminal session, run `conda activate dmred` once, verify it's active (`$CONDA_DEFAULT_ENV` should equal `dmred`), then run Python/pip/pytest commands directly without prefixing them with `conda run -n dmred`.

There is no `requirements.txt`/`pyproject.toml` dependency list checked in — `pyproject.toml` only holds pytest config. Assume dependencies (numpy, scikit-learn, umap-learn, dscribe, ase, pymatgen, mp-api, jax, flax, optax, learned_optimization, matplotlib, pyxtal, jupyter/nbformat/nbconvert/ipykernel) are already installed in the `dmred` environment; don't try to `pip install -e .[dev]` as described in the (stale) README. `pyxtal` (random symmetric-structure generation, not otherwise used by `dim_red` itself) and the notebook tooling were added specifically to build/run `examples/pyxtal_structure_generation.ipynb`.

## Commands

Run all tests (from repo root, `dmred` active — `pythonpath = ["src"]` in `pyproject.toml` makes the package importable without installation):

```bash
pytest
pytest -v
```

Run a single test file or test:

```bash
pytest tests/test_pca.py
pytest tests/test_pca.py::test_pca_fit_transform -v
```

Some test modules guard optional/heavy dependencies with `pytest.importorskip` (`test_umap.py` skips without `umap`; `test_vae_model.py`/`test_vae_training.py` skip without `jax`) — if those deps aren't in the active env, those tests silently skip rather than fail.

`tests/conftest.py`'s `_fast_optimizer_for_training_tests` autouse fixture swaps VeLO for a plain `optax.adam` in every test (see the fixture's own docstring for why -- training tests would otherwise take ~15-18s vs ~3s per call); a no-op when jax/learned_optimization aren't installed, and production code itself is untouched.

Pre-commit hooks are configured in `.pre-commit-config.yaml`. Run `pre-commit run --all-files` before committing if hooks aren't installed as a git hook.

The `MP_API_KEY` environment variable is required for any code path that calls `dim_red.fetch` / `run_pca_reduction` against the real Materials Project API (see `examples/run_analysis_demo.py`). Tests mock `MPRester`, so they don't need it.

## Architecture

`src/dim_red/` is a materials-science dimensionality-reduction toolkit with two independent verticals joined by an analysis workflow:

- **Data ingestion** (`fetch.py`): pulls crystal structures from the Materials Project API (`mp_api`) filtered by crystal system, converts pymatgen `Structure` objects to ASE `Atoms` via `AseAtomsAdaptor`, and stashes the `material_id` on `atoms.info`.
- **`augmentation.py`**: diversifies a fetched (or generated) structure database via data augmentation — `augment_structures`/`AugmentationConfig` apply configurable-probability positional jitter (simulated thermal noise: small Gaussian displacements of every atom) and/or vacancy (random atom removal) to each structure, producing `n_augmented` tagged copies per input (`fetch_and_augment_structures` chains this right after `fetch_structures_by_crystal_system`). `_augment_once` guarantees every augmented copy has at least one of jitter/vacancy actually applied to it (independent probability rolls for each; if *neither* succeeds, one is forced on rather than the copy coming out identical to the original) — the corollary being that if only one mechanism is configured at all (`jitter_std > 0` xor `vacancy_atom_probability > 0`), that one applies to every augmented copy regardless of its own probability, since it's the only thing that can be forced. Vacancy removal is capped by `max_vacancies` (`None` default = uncapped) rather than a minimum-atoms floor — it always keeps at least 1 atom regardless of that cap, but doesn't otherwise guarantee a minimum count. If `AugmentationConfig.supercell_radius` is set, `augment_structures` first runs every input structure through `make_supercell_for_radius` (once per structure, before building the kept-original copy and any augmented ones) -- repeats the cell an integer number of times along each periodic lattice vector so a sphere of that radius (Angstroms) fits inside without touching its own periodic image (the standard "perpendicular cell width >= 2 * radius" sizing rule, computed independently per axis off the *original* unrepeated cell since repeating other axes doesn't change a given axis's perpendicular width). Meant for unit cells too small to meaningfully augment -- pyxtal can generate cells holding as few as 1-2 atoms -- `None` (default) skips this step, current behavior unchanged. Wired into the pipeline via `RunConfig.augmentation` (YAML: top-level `augmentation:` block, `pipeline.config.AugmentationConfig` -- kept as its own dataclass mirroring `dim_red.augmentation.AugmentationConfig` one-to-one, same reasoning as `PyxtalConfig` mirroring `GenerationConfig`, so `pipeline.config` doesn't pull in `dim_red.augmentation`'s import chain, i.e. `dim_red.fetch` -> `mp_api`/`pymatgen`, just to parse a config); `None` (default) disables it, current behavior unchanged. `pipeline.dataset_cache.build_dataset_for_run`'s `_resolve_augmentation` converts it to the real `dim_red.augmentation.AugmentationConfig` and resolves `seed` the same way `PyxtalConfig.seed` does (falls back to `RunConfig.seed` when unset), then both `get_or_build_dataset`/`get_or_build_pyxtal_dataset` run `augment_structures` on the fetched/generated structures right before SOAP -- applies regardless of `data_source`. The augmentation settings are folded into the dataset cache key, so a config that changes only `augmentation` doesn't reuse a cache built without it (or with different settings).
- **Featurization** (`soap.py`): computes SOAP (Smooth Overlap of Atomic Positions) descriptors from `Atoms` objects using `dscribe`. Has an optional `normalize_distances` preprocessing step that rescales atomic positions so the nearest-neighbor distance is 1.0, making descriptors invariant to absolute bond-length scale.
- **Classical dimensionality reduction** (`pca.py`, `umap.py`, `utils.py`): thin, fit/transform-style wrapper classes around scikit-learn's `PCA` and `umap-learn`'s `UMAP`, both validating `n_components` and raising if used before fitting. `UMAP.__init__` also takes optional `n_neighbors`/`min_dist`/`metric`/`random_state`, each `None` by default -- left unset, that hyperparameter is whatever `umap-learn` itself defaults to (rather than this wrapper re-picking its own defaults), and only the ones actually given get forwarded to the underlying `SklearnUMAP`. `utils.standardize` does z-score normalization and is the shared preprocessing step before either reduction.
- **`analysis/`**: see `src/dim_red/analysis/CLAUDE.md`.
- **`generate.py`**: an alternative to `fetch.py` for building a structure database — generates synthetic, symmetry-valid structures from scratch with `pyxtal` (`GenerationConfig`/`generate_structures`) instead of querying Materials Project, returning the same `List[Atoms]` shape (`info["material_id"]`/`info["spacegroup"]`, plus `info["family"]`) so it's a drop-in alternative downstream. Configurable per-space-group or per-family (with uniform/random splitting across a family's space groups) structure counts, and how many chemical species per structure (which elements doesn't matter — sampled from a placeholder pool). Logs a warning for any space group whose Wyckoff multiplicities couldn't accommodate the requested structures. Not a hard dim_red dependency — requires `pip install pyxtal`. See `examples/pyxtal_structure_generation.ipynb` for a guided walkthrough, and `pipeline/dataset_cache.py`'s `RunConfig.data_source == "pyxtal"` for its pipeline integration: `RunConfig.fetch`/`RunConfig.pyxtal` are symmetric, data-source-specific config blocks (`pipeline/config.py`'s `FetchConfig`/`PyxtalConfig`), exactly one of which must be set matching `data_source` (YAML: `fetch:`/`pyxtal:` top-level blocks — `crystal_systems`/`limit_per_system`/`api_key` now live under `fetch:`, not a flat top level).
- **`vae/`**: see `src/dim_red/vae/CLAUDE.md`.
- **`autoencoder/`**: see `src/dim_red/autoencoder/CLAUDE.md`.
- **`supcon/`**: see `src/dim_red/supcon/CLAUDE.md`.

`pipeline.tail_training` (phase 2 of the SupCon body/tail workflow) and `RunConfig.tails` (auto-invoking phase 2 from `dimred-run`/`dimred-sweep`) are documented in `src/dim_red/pipeline/CLAUDE.md`.

**Optimizer selection** is implemented identically (duplicated `_make_optimizer(optimizer, learning_rate, num_steps)` helper, same field names, same semantics) in all four training-loop modules (`vae.training`, `autoencoder.training`, `supcon.training` (phase 1, body+projection tail), `supcon.tail_training` (phase 2, both `train_classification_tail`/`train_visualization_tail`)), via each module's own `TrainConfig`/`TailTrainConfig.optimizer` field: `"adam"` (default) builds a plain `optax.adam(learning_rate)`, wrapped in `optax.with_extra_args_support` so it still accepts the `extra_args={"loss": ...}` kwarg every `_make_train_step`/`_make_eval_step` always passes to `tx.update` (VeLO is loss-conditioned; a bare `optax.adam` doesn't accept `extra_args` at all -- this wrapping is what lets every train/eval step's code stay completely unchanged regardless of which optimizer is active); `"velo"` builds `learned_optimization`'s pretrained VeLO meta-learned optimizer via `prefab.optax_lopt(num_steps=...)`, unchanged from this codebase's original (and, before this feature, only) behavior. `"adam"` became the default because VeLO's setup -- importing `learned_optimization`, then loading its pretrained hypernetwork checkpoint -- costs several fixed seconds at minimum before any training starts, and on some networks additionally attempts to resolve Google Cloud credentials in a way that can hang far longer if that path is slow/unreachable rather than failing instantly; this cost is fixed per training call regardless of problem size, so it's proportionally worst for phase-2 tail training (tiny single-hidden-layer MLPs, where a meta-learned optimizer buys nothing). `learning_rate` (already a pre-existing field in every one of these `TrainConfig`s, previously documented as merely "kept for API compatibility") is now Adam's actual learning rate whenever `optimizer == "adam"`; it stays unused when `optimizer == "velo"`. `pipeline.config.TrainSettings.optimizer`/`TailTrainSettings.optimizer` (both `"adam"` default, both validated in `__post_init__` against a shared `_OPTIMIZER_KINDS = ("adam", "velo")` tuple) are the single config-layer fields `pipeline.single_run.run_single`/`pipeline.tail_training.train_tail` read to populate whichever `TrainConfig`/`TailTrainConfig` the active `model_kind`/`tail_kind` uses, and both log it (`optimizer=%s`) alongside their other training-start log lines. **This is a deliberate default-behavior change**: any pre-existing config that doesn't set `train.optimizer` explicitly now trains with Adam instead of VeLO -- set `train.optimizer: velo` to opt back into the original behavior.

**Early stopping** is implemented identically (duplicated code, same field names, same semantics) in all three training loops (`vae.training.train_vae`, `autoencoder.training.train_autoencoder`, `supcon.training.train_supcon`), via four `TrainConfig` fields: `early_stopping` (bool, default `False`), `early_stopping_patience`, `early_stopping_min_delta`, `early_stopping_restore_best`. It always monitors `val_loss` (the full weighted objective each history dict already always has) — not configurable to a different metric in this first pass. Mechanism: after each epoch, if `val_loss < best_val_loss - min_delta` the counter resets (and, if `restore_best_weights`, that epoch's `params` are snapshotted by reference — cheap, since `optax.apply_updates` returns a fresh pytree each step rather than mutating in place); otherwise the counter increments, and once it reaches `patience` the epoch loop `break`s. `model.params` is set to the snapshotted best params at the end when `restore_best_weights` is True (regardless of whether the loop broke early or ran to `epochs`), otherwise to the last epoch's. Returned `history` dicts are simply shorter than `config.epochs` when stopped early — `_save_loss_history` (CSV writer) already derives its row count from the history dict itself, but `pipeline.single_run.run_single`'s per-epoch console/`run.log` logging loop must use `len(history["train_loss"])`, not `config.train.epochs`, or it would index past the end. `pipeline.config.EarlyStoppingConfig` (YAML: `train.early_stopping: {enabled, patience, min_delta, restore_best_weights}`, nested under the existing `train:` block since it's training-loop mechanics like `epochs`/`batch_size`) is the single config-layer source `run_single` reads to populate whichever `TrainConfig` the active `model_kind` uses — default `enabled: false` keeps every pre-existing config backward compatible. `total_steps` for VeLO's `prefab.optax_lopt(num_steps=...)` is still computed from the *configured* `epochs` (not adjusted for early stopping) since it's just a progress-normalization signal for VeLO's learned schedule, not a hard requirement to reach. Caveat for `pipeline.compare`: its "final metric" plots/CSVs read `loss_history[metric][-1]` (the last *logged* epoch) unchanged -- with `restore_best_weights=True` that can be a worse value than what the actually-restored `model.params` achieved a few epochs earlier, since the CSV still records every epoch including the non-improving ones that triggered the stop.

`pipeline.inference` (applying an already-trained run's model to new structures) is documented in `src/dim_red/pipeline/CLAUDE.md`.

`dim_red/__init__.py` lazily imports `soap`, `fetch`, `analysis`, `vae`, `autoencoder`, and `supcon` via module-level `__getattr__` (PEP 562) so that importing the base package doesn't require optional heavy dependencies (dscribe, mp_api, jax, flax, etc.) unless those submodules are actually used. `vae/__init__.py`, `autoencoder/__init__.py`, and `supcon/__init__.py` do the same lazy pattern internally for their own symbols. When adding new public symbols to any of these packages, follow this lazy-import pattern rather than importing eagerly at module top.
