## Environment

This project must be run inside the conda environment `dmred` (located at `/home/seraftu/miniconda3/envs/dmred`). In a persistent terminal session, run `conda activate dmred` once, verify it's active (`$CONDA_DEFAULT_ENV` should equal `dmred`), then run Python/pip/pytest commands directly without prefixing them with `conda run -n dmred`.

Dependencies are declared in `pyproject.toml` (core + extras); assume everything needed (numpy, scikit-learn, umap-learn, dscribe, ase, pymatgen, mp-api, jax, flax, optax, matplotlib, pyxtal, jupyter/nbformat/nbconvert/ipykernel) is already installed in the `dmred` environment and don't `pip install` anything. `mace_jax` is optional and only needed for `model_kind: supcon_mace`.

## Commands

Run all tests (from repo root, `dmred` active — `pythonpath = ["src"]` in `pyproject.toml` makes the package importable without installation):

```bash
pytest
pytest -v
```

Run a single test file or test:

```bash
pytest tests/test_pca.py
pytest tests/test_pca.py::test_pca_fit_transform -v
```

Some test modules guard optional/heavy dependencies with `pytest.importorskip` (`test_umap.py` skips without `umap`; the jax-based tests skip without `jax`) — if those deps aren't in the active env, those tests silently skip rather than fail.

Pre-commit hooks are configured in `.pre-commit-config.yaml`. Run `pre-commit run --all-files` before committing if hooks aren't installed as a git hook.

The `MP_API_KEY` environment variable is required for any code path that calls `dim_red.fetch` against the real Materials Project API . Tests mock `MPRester`, so they don't need it.

## Architecture

`src/dim_red/` is a materials-science dimensionality-reduction toolkit with several model kinds sharing one pipeline:

- **Data ingestion** (`fetch.py`): pulls crystal structures from the Materials Project API (`mp_api`) filtered by crystal system, converts pymatgen `Structure` objects to ASE `Atoms` via `AseAtomsAdaptor`, and stashes the `material_id` on `atoms.info`.
- **`augmentation.py`**: diversifies a fetched (or generated) structure database via data augmentation — `augment_structures`/`AugmentationConfig` apply configurable-probability positional jitter (simulated thermal noise: small Gaussian displacements of every atom) and/or vacancy (random atom removal) to each structure, producing `n_augmented` tagged copies per input . `_augment_once` guarantees every augmented copy has at least one of jitter/vacancy actually applied to it (independent probability rolls for each; if *neither* succeeds, one is forced on rather than the copy coming out identical to the original) — the corollary being that if only one mechanism is configured at all (`jitter_std > 0` xor `vacancy_atom_probability > 0`), that one applies to every augmented copy regardless of its own probability, since it's the only thing that can be forced. Vacancy removal is capped by `max_vacancies` (`None` default = uncapped) rather than a minimum-atoms floor — it always keeps at least 1 atom regardless of that cap, but doesn't otherwise guarantee a minimum count. If `AugmentationConfig.supercell_radius` is set, `augment_structures` first runs every input structure through `make_supercell_for_radius` (once per structure, before building the kept-original copy and any augmented ones) -- repeats the cell an integer number of times along each periodic lattice vector so a sphere of that radius (Angstroms) fits inside without touching its own periodic image (the standard "perpendicular cell width >= 2 * radius" sizing rule, computed independently per axis off the *original* unrepeated cell since repeating other axes doesn't change a given axis's perpendicular width). Meant for unit cells too small to meaningfully augment -- pyxtal can generate cells holding as few as 1-2 atoms -- `None` (default) skips this step, current behavior unchanged. Wired into the pipeline via `RunConfig.augmentation` (YAML: top-level `augmentation:` block, `pipeline.config.AugmentationConfig` -- kept as its own dataclass mirroring `dim_red.augmentation.AugmentationConfig` one-to-one, same reasoning as `PyxtalConfig` mirroring `GenerationConfig`, so `pipeline.config` doesn't pull in `dim_red.augmentation`'s import chain, i.e. `dim_red.fetch` -> `mp_api`/`pymatgen`, just to parse a config); `None` (default) disables it, current behavior unchanged. `pipeline.dataset_cache.build_dataset_for_run`'s `_resolve_augmentation` converts it to the real `dim_red.augmentation.AugmentationConfig` and resolves `seed` the same way `PyxtalConfig.seed` does (falls back to `RunConfig.seed` when unset), then both `get_or_build_dataset`/`get_or_build_pyxtal_dataset` run `augment_structures` on the fetched/generated structures right before SOAP -- applies regardless of `data_source`. The augmentation settings are folded into the dataset cache key, so a config that changes only `augmentation` doesn't reuse a cache built without it (or with different settings).
- **Featurization** (`soap.py`): computes SOAP (Smooth Overlap of Atomic Positions) descriptors from `Atoms` objects using `dscribe`.
- **Classical dimensionality reduction** (`pca.py`, `umap.py`, `utils.py` (z-score `fit_standardization`/`apply_standardization`)): thin, fit/transform-style wrapper classes around scikit-learn's `PCA` and `umap-learn`'s `UMAP`, both validating `n_components` and raising if used before fitting. `UMAP.__init__` also takes optional `n_neighbors`/`min_dist`/`metric`/`random_state`, each `None` by default -- left unset, that hyperparameter is whatever `umap-learn` itself defaults to (rather than this wrapper re-picking its own defaults), and only the ones actually given get forwarded to the underlying `SklearnUMAP`.
- **`analysis/`**: see `src/dim_red/analysis/CLAUDE.md`.
- **`generate.py`**: an alternative to `fetch.py` for building a structure database — generates synthetic, symmetry-valid structures from scratch with `pyxtal` (`GenerationConfig`/`generate_structures`) instead of querying Materials Project, returning the same `List[Atoms]` shape (`info["material_id"]`/`info["spacegroup"]`, plus `info["family"]`) so it's a drop-in alternative downstream. Configurable per-space-group or per-family (with uniform/random splitting across a family's space groups) structure counts, and how many chemical species per structure (which elements doesn't matter — sampled from a placeholder pool). Logs a warning for any space group whose Wyckoff multiplicities couldn't accommodate the requested structures. Not a hard dim_red dependency — requires `pip install pyxtal`. See `examples/pyxtal_structure_generation.ipynb` for a guided walkthrough, and `pipeline/dataset_cache.py`'s `RunConfig.data_source == "pyxtal"` for its pipeline integration: `RunConfig.fetch`/`RunConfig.pyxtal` are symmetric, data-source-specific config blocks (`pipeline/config.py`'s `FetchConfig`/`PyxtalConfig`), exactly one of which must be set matching `data_source` (YAML: `fetch:`/`pyxtal:` top-level blocks — `crystal_systems`/`limit_per_system`/`api_key` now live under `fetch:`, not a flat top level).
- **`supcon/`**: see `src/dim_red/supcon/CLAUDE.md`.
- **`cgcnn/`**: see `src/dim_red/cgcnn/CLAUDE.md`.
- **`mace/`**: see `src/dim_red/mace/CLAUDE.md`. A frozen, pretrained equivariant encoder (external `mace_jax` package, optional) whose embeddings feed `model_kind: supcon_mace` — the SupCon recipe on MACE embeddings, reusing all of `supcon/`.

`pipeline.tail_training` (phase 2 of the SupCon body/tail workflow, incl. the `hierarchical_supcon` per-family experts) and `RunConfig.tails` (auto-invoking phase 2 from `dimred-run`/`dimred-sweep`) are documented in `src/dim_red/pipeline/CLAUDE.md`.

**Optimizer**: always `optax.adam(learning_rate)` (VeLO was removed; a saved `train.optimizer` key is ignored). Family-level models and per-family experts are meant to be the same encoder + projection + visualization + classifier stack with one implementation; the refactor list is in `REFACTOR_TODO.md`.

**Early stopping** is implemented identically (duplicated code, same field names, same semantics) in the training loops (`supcon.training.training_first_phase`, `cgcnn.training.train_cgcnn`, plus the phase-2 tail loops), via four `TrainConfig` fields: `early_stopping` (bool, default `False`), `early_stopping_patience`, `early_stopping_min_delta`, `early_stopping_restore_best`. It always monitors `val_loss` (the full weighted objective each history dict already always has) — not configurable to a different metric in this first pass. Mechanism: after each epoch, if `val_loss < best_val_loss - min_delta` the counter resets (and, if `restore_best_weights`, that epoch's `params` are snapshotted by reference — cheap, since `optax.apply_updates` returns a fresh pytree each step rather than mutating in place); otherwise the counter increments, and once it reaches `patience` the epoch loop `break`s. `model.params` is set to the snapshotted best params at the end when `restore_best_weights` is True (regardless of whether the loop broke early or ran to `epochs`), otherwise to the last epoch's. Returned `history` dicts are simply shorter than `config.epochs` when stopped early — `_save_loss_history` (CSV writer) already derives its row count from the history dict itself, but `pipeline.single_run.run_single`'s per-epoch console/`run.log` logging loop must use `len(history["train_loss"])`, not `config.train.epochs`, or it would index past the end. `pipeline.config.EarlyStoppingConfig` (YAML: `train.early_stopping: {enabled, patience, min_delta, restore_best_weights}`, nested under the existing `train:` block since it's training-loop mechanics like `epochs`/`batch_size`) is the single config-layer source `run_single` reads to populate whichever `TrainConfig` the active `model_kind` uses — default `enabled: false` keeps every pre-existing config backward compatible. Caveat for `pipeline.compare`: its "final metric" plots/CSVs read `loss_history[metric][-1]` (the last *logged* epoch) unchanged -- with `restore_best_weights=True` that can be a worse value than what the actually-restored `model.params` achieved a few epochs earlier, since the CSV still records every epoch including the non-improving ones that triggered the stop.

`pipeline.inference` (applying an already-trained run's model to new structures) is documented in `src/dim_red/pipeline/CLAUDE.md`.

`dim_red/__init__.py` lazily imports `soap`, `fetch`, `analysis`, `supcon`, and `cgcnn` via module-level `__getattr__` (PEP 562) so that importing the base package doesn't require optional heavy dependencies (dscribe, mp_api, jax, flax, etc.) unless those submodules are actually used. `supcon/__init__.py` and `cgcnn/__init__.py` do the same lazy pattern internally for their own symbols. When adding new public symbols to any of these packages, follow this lazy-import pattern rather than importing eagerly at module top.
