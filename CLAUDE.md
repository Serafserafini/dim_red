## Environment

This project must be run inside the conda environment `dmred` (located at `/home/seraftu/miniconda3/envs/dmred`). In a persistent terminal session, run `conda activate dmred` once, verify it's active (`$CONDA_DEFAULT_ENV` should equal `dmred`), then run Python/pip/pytest commands directly without prefixing them with `conda run -n dmred`.

There is no `requirements.txt`/`pyproject.toml` dependency list checked in — `pyproject.toml` only holds pytest config. Assume dependencies (numpy, scikit-learn, umap-learn, dscribe, ase, pymatgen, mp-api, jax, flax, optax, learned_optimization, matplotlib, pyxtal, jupyter/nbformat/nbconvert/ipykernel) are already installed in the `dmred` environment; don't try to `pip install -e .[dev]` as described in the (stale) README. `pyxtal` (random symmetric-structure generation, not otherwise used by `dim_red` itself) and the notebook tooling were added specifically to build/run `examples/pyxtal_structure_generation.ipynb`.


Run a single test file or test:

## Architecture

`src/dim_red/` is a materials-science dimensionality-reduction toolkit with two independent verticals joined by an analysis workflow:

- **Data ingestion** (`fetch.py`): pulls crystal structures from the Materials Project API (`mp_api`) filtered by crystal system, converts pymatgen `Structure` objects to ASE `Atoms` via `AseAtomsAdaptor`, and stashes the `material_id` on `atoms.info`.
- **`augmentation.py`**: diversifies a fetched (or generated) structure database via data augmentation — `augment_structures`/`AugmentationConfig` apply configurable-probability positional jitter and/or vacancy (random atom removal) to each structure, producing `n_augmented` tagged copies per input (`fetch_and_augment_structures` chains this right after `fetch_structures_by_crystal_system`).
- **Featurization** (`soap.py`): computes SOAP (Smooth Overlap of Atomic Positions) descriptors from `Atoms` objects using `dscribe`. Has an optional `normalize_distances` preprocessing step that rescales atomic positions so the nearest-neighbor distance is 1.0, making descriptors invariant to absolute bond-length scale.
- **Classical dimensionality reduction** (`pca.py`, `umap.py`, `utils.py`): thin, fit/transform-style wrapper classes around scikit-learn's `PCA` and `umap-learn`'s `UMAP`, both validating `n_components` and raising if used before fitting. `UMAP.__init__` also takes optional `n_neighbors`/`min_dist`/`metric`/`random_state`, each `None` by default -- left unset, that hyperparameter is whatever `umap-learn` itself defaults to (rather than this wrapper re-picking its own defaults), and only the ones actually given get forwarded to the underlying `SklearnUMAP`. `utils.standardize` does z-score normalization and is the shared preprocessing step before either reduction.
- **`analysis/`**: glues the above into an end-to-end pipeline. `workflow.run_pca_reduction` fetches structures per crystal system → computes SOAP vectors (species auto-detected across all fetched structures) → standardizes → PCA-reduces, returning `(X_reduced, labels, material_ids)`. `plotting.plot_reduced_space` renders a 2D scatter colored by label; `plotting.plot_spacegroup_histogram` renders a spacegroup-count bar chart colored by crystal family. `examples/run_analysis_demo.py` shows the intended top-level usage.
- **`generate.py`**: an alternative to `fetch.py` for building a structure database — generates synthetic, symmetry-valid structures from scratch with `pyxtal` (`GenerationConfig`/`generate_structures`) instead of querying Materials Project, returning the same `List[Atoms]` shape (`info["material_id"]`/`info["spacegroup"]`, plus `info["family"]`) so it's a drop-in alternative downstream. Configurable per-space-group or per-family (with uniform/random splitting across a family's space groups) structure counts, and how many chemical species per structure (which elements doesn't matter — sampled from a placeholder pool). Logs a warning for any space group whose Wyckoff multiplicities couldn't accommodate the requested structures. Not a hard dim_red dependency — requires `pip install pyxtal`. See `examples/pyxtal_structure_generation.ipynb` for a guided walkthrough, and `pipeline/dataset_cache.py`'s `RunConfig.data_source == "pyxtal"` for its pipeline integration: `RunConfig.fetch`/`RunConfig.pyxtal` are symmetric, data-source-specific config blocks (`pipeline/config.py`'s `FetchConfig`/`PyxtalConfig`), exactly one of which must be set matching `data_source` (YAML: `fetch:`/`pyxtal:` top-level blocks — `crystal_systems`/`limit_per_system`/`api_key` now live under `fetch:`, not a flat top level).
- **`vae/`**: a separate, JAX/Flax-based neural dimensionality reduction path, independent of the PCA/UMAP/SOAP pipeline (it operates on arbitrary feature matrices via `VAEDatabase`, not specifically SOAP output):
  - `model.py`: `VAEModule` (Flax `nn.Module`) composing `EncoderModule`/`DecoderModule` MLPs with configurable hidden-layer sequences; `VAE` is the high-level wrapper holding `params` and exposing `encode`/`decode`/`forward` plus `*_with_params` variants for use inside jitted training steps. Decoder hidden dims default to the mirror (reverse) of the encoder's unless `mirror=False`.
  - `codec.py`: `split_encoder_decoder` produces standalone `VAEEncoder`/`VAEDecoder` callables from a trained `VAE` for downstream use without exposing the full model.
  - `database.py`: `VAEDatabase` wraps a `(n_samples, n_features)` array and provides a reproducible `train_val_split`.
  - `training.py`: `train_vae` runs a full train/val loop using `learned_optimization`'s VeLO meta-learned optimizer (via `prefab.optax_lopt`) as the optimizer backend — note `TrainConfig.learning_rate` is unused by VeLO and kept only for API compatibility. Batches are jitted with `jax.jit`/`jax.vmap`; validation batches are padded to a fixed size with a mask so `vmap` can process a whole epoch in one call. `TrainConfig.device` selects the JAX backend (`"cpu"`/`"gpu"`) and training raises if no matching JAX device exists.
- **`autoencoder/`**: a deterministic (non-variational) counterpart to `vae/`, mirroring its exact module layout and public API shape (`model.py`'s `Autoencoder`/`Encoder`/`Decoder`, `codec.py`'s `split_encoder_decoder`, `training.py`'s `TrainConfig`/`train_autoencoder`) so the two are interchangeable. The only real difference: `Autoencoder.encode` returns a single deterministic `z` (not a sampled `(mu, logvar)` posterior), so there's no KL term, no `beta`, and no PRNG key needed at encode/decode/forward time. Reuses `vae.database.VAEDatabase` directly (dataset handling has nothing model-specific about it) rather than duplicating it. `pipeline.single_run.run_single` picks between `vae`/`autoencoder` via `RunConfig.model_kind` (YAML: top-level `model: vae` or `model: autoencoder`, default `vae`); both read architecture from the same `vae:` config block and aux-heads from the same `aux_heads:` block, so a sweep can vary `model` like any other grid axis (see `configs/single_run_autoencoder.example.yaml`).
- **`supcon/`**: an encoder-only counterpart to `vae/`/`autoencoder/` — no decoder, no reconstruction loss, no KL/`beta`/classifier heads at all. Trains purely for a good latent space: same-family/same-spacegroup structures pulled together, others pushed apart, via a Supervised Contrastive (SupCon) loss computed directly on the encoder's latent `z`.
  - `model.py`: `EncoderModule` (Flax `nn.Module`, deliberately duplicated from `autoencoder.model.EncoderModule` rather than imported, so this package stays independent of `vae`/`autoencoder`) plus `SupConEncoder`, the high-level wrapper (`params`, `encode`/`encode_with_params`). No `Decoder`, no `ClassifierHead`, no `codec.py` — `SupConEncoder.encode` is already the only artifact worth exporting.
  - `training.py`: `TrainConfig` (`epochs`/`batch_size`/`learning_rate` — unused, VeLO again — /`tau`/`seed`/`device`; deliberately *without* `lambda_family`/`lambda_spacegroup`/`lambda_norm`, which live in `pipeline.config.SupConConfig` instead and are passed to `train_supcon` as explicit arguments — none of the three are training-loop mechanics like `tau`, they're loss-term weights). `supcon_loss(z, labels, tau)` implements Supervised Contrastive (Khosla et al. 2020) with a *negative squared-Euclidean-distance* similarity (`-||z_i - z_j||^2 / tau`, not the more common cosine-similarity formulation — no internal L2-normalization of `z`), and for each anchor sums over same-label positives in the batch (self excluded) normalized by a log-sum-exp over every other batch row. An anchor with no positive in its batch is excluded from that term's mean (not zeroed-and-diluted) — implemented by dividing by the count of anchors that *did* have a positive, not the batch size. A large finite negative sentinel (not `-jnp.inf`) masks self-comparisons before `log_softmax`, since `0 * -inf` is NaN in the forward pass, not just the gradient — a real pitfall if you touch this function. Because this similarity has no built-in scale normalization, `norm_penalty(z)` (`mean(sum(z**2, axis=-1))`) is available as an optional regularizer, weighted by `lambda_norm` (`0.0` — disabled — by default, unlike `lambda_family`/`lambda_spacegroup` not gated by `mode` since it doesn't depend on labels at all) and added to `total` in both `_make_train_step`/`_make_eval_step` identically, so `val_loss` reflects the same objective actually optimized; `train_norm_penalty`/`val_norm_penalty` are always in `history`, regardless of `lambda_norm`, for diagnosing unbounded embedding growth even when the penalty itself is off. `train_supcon` mirrors `train_vae`/`train_autoencoder`'s `has_family`/`has_spacegroup` compile-time-branch pattern and VeLO optimizer setup, but deliberately does **not** reuse their padding+`vmap`-over-epoch validation trick: SupCon is pairwise *within* a batch, so a zero-padded dummy row would become a spurious positive/negative for real rows (unlike MSE/cross-entropy, computed independently per row). Both train and validation instead use a plain unpadded batch loop (one jitted call per batch), epoch metrics combined as a batch-size-weighted mean.
  - `sampling.py`: an alternative to plain random shuffling for *training* batches only (validation batches always stay random, regardless), selected via `BatchingConfig.strategy == "balanced"` (`pipeline.config`). `iter_balanced_batches`/`balanced_batch_indices` build each batch as `P` families x `K` examples per family (optionally further stratified into `S` spacegroups per family, `K // S` examples each — the remainder `K % S` going to the first few chosen spacegroups when it doesn't divide evenly), so the SupCon loss reliably has positives available for every anchor even on less-balanced datasets. `P`/`S` are clamped down (with a `logger.warning`) to what's actually present if the configured value exceeds it. Row sampling is without replacement when the pool is large enough, with replacement only when necessary (a small family/spacegroup). Uses `logging.getLogger("dim_red.pipeline")` — the same logger name every other pipeline module uses, not a `dim_red.supcon`-prefixed one — purely so these warnings land in a run's `run.log` (a plain `logging` name, not an import, so this doesn't create a dependency on `dim_red.pipeline`).
  - Reuses `vae.database.VAEDatabase` directly, same as `autoencoder`.
  - `pipeline.single_run.run_single` integrates `model_kind == "supcon"` as a third branch alongside `vae`/`autoencoder` (model construction, `train_config`, the training call, and `_log_epoch`'s per-history-key logging), all additive — the `vae`/`autoencoder` branches are untouched. It reads its encoder architecture from the same `vae:` block (`decoder_hidden_dim`/`mirror` ignored, like `autoencoder` ignores `beta`) but its own `supcon:` block (YAML: `mode` — `"family_only"`/`"spacegroup_only"`/`"family_and_spacegroup"`, mirroring `aux_heads.mode`'s shape but independent per term, since there's no family→spacegroup masking to require family whenever spacegroup is active — plus `lambda_family`/`lambda_spacegroup`/`tau`/`lambda_norm`) instead of `aux_heads:`, and its batch-sampling strategy from `batching:` (`pipeline.config.BatchingConfig` — `strategy: random` (default) or `balanced`, plus `balanced_params: {P, K, S}`; ignored for `vae`/`autoencoder`, which always shuffle). Since there are no classifier heads, `run_single`'s family/spacegroup-probability inference block is skipped entirely for this `model_kind`; `embeddings.npz` keeps only the base fields (`embeddings`/`features`/`labels`/`material_ids`/`spacegroups`/`split`), no `*_probs`/`*_classes`. Note `train_supcon`'s `train_family_ids`/`train_spacegroup_ids` (which family/spacegroup terms the *loss* uses) are deliberately independent of its `batching_family_ids`/`batching_spacegroup_ids` (which labels *batches* are grouped by) — `run_single` builds family/spacegroup vocab ids whenever either is needed, so e.g. `supcon.mode: spacegroup_only` + `batching.strategy: balanced` still groups batches by family even though the family loss term itself stays inactive. See `configs/single_run_supcon.example.yaml`/`configs/sweep_supcon.example.yaml`.

**Early stopping** is implemented identically (duplicated code, same field names, same semantics) in all three training loops (`vae.training.train_vae`, `autoencoder.training.train_autoencoder`, `supcon.training.train_supcon`), via four `TrainConfig` fields: `early_stopping` (bool, default `False`), `early_stopping_patience`, `early_stopping_min_delta`, `early_stopping_restore_best`. It always monitors `val_loss` (the full weighted objective each history dict already always has) — not configurable to a different metric in this first pass. Mechanism: after each epoch, if `val_loss < best_val_loss - min_delta` the counter resets (and, if `restore_best_weights`, that epoch's `params` are snapshotted by reference — cheap, since `optax.apply_updates` returns a fresh pytree each step rather than mutating in place); otherwise the counter increments, and once it reaches `patience` the epoch loop `break`s. `model.params` is set to the snapshotted best params at the end when `restore_best_weights` is True (regardless of whether the loop broke early or ran to `epochs`), otherwise to the last epoch's. Returned `history` dicts are simply shorter than `config.epochs` when stopped early — `_save_loss_history` (CSV writer) already derives its row count from the history dict itself, but `pipeline.single_run.run_single`'s per-epoch console/`run.log` logging loop must use `len(history["train_loss"])`, not `config.train.epochs`, or it would index past the end. `pipeline.config.EarlyStoppingConfig` (YAML: `train.early_stopping: {enabled, patience, min_delta, restore_best_weights}`, nested under the existing `train:` block since it's training-loop mechanics like `epochs`/`batch_size`) is the single config-layer source `run_single` reads to populate whichever `TrainConfig` the active `model_kind` uses — default `enabled: false` keeps every pre-existing config backward compatible. `total_steps` for VeLO's `prefab.optax_lopt(num_steps=...)` is still computed from the *configured* `epochs` (not adjusted for early stopping) since it's just a progress-normalization signal for VeLO's learned schedule, not a hard requirement to reach. Caveat for `pipeline.compare`: its "final metric" plots/CSVs read `loss_history[metric][-1]` (the last *logged* epoch) unchanged -- with `restore_best_weights=True` that can be a worse value than what the actually-restored `model.params` achieved a few epochs earlier, since the CSV still records every epoch including the non-improving ones that triggered the stop.

`dim_red/__init__.py` lazily imports `soap`, `fetch`, `analysis`, `vae`, `autoencoder`, and `supcon` via module-level `__getattr__` (PEP 562) so that importing the base package doesn't require optional heavy dependencies (dscribe, mp_api, jax, flax, etc.) unless those submodules are actually used. `vae/__init__.py`, `autoencoder/__init__.py`, and `supcon/__init__.py` do the same lazy pattern internally for their own symbols. When adding new public symbols to any of these packages, follow this lazy-import pattern rather than importing eagerly at module top.
